Chapter 16

A library people can actually use

A component that nobody can find, understand or trust might as well not exist. This chapter is about the everyday side of a growing library: organising it, documenting it, tracking it, and handling the moment a team needs something a little different.

Read this if

Your Figma library has grown messy, people keep building their own versions of things that already exist, or you're not sure which components are really being used.

What you'll leave with
  1. A way to organise and name a design library so people can find things fast.
  2. A documentation template and a simple life cycle for every component.
  3. Practical ways to track usage and to handle teams that need something different.

16.1If people can't find it, they'll rebuild it

Here's a pattern we see in almost every growing design system. In year one, the Figma library is small and everyone knows what's in it. By year three, it has hundreds of components, several abandoned experiments, old versions nobody deleted, and names that made sense to whoever created them.

ScenarioThe designer who couldn't find the right component
The situation

Meera joins as a product designer. She needs a simple tag to show an invoice's status. She opens the library and searches "tag".

What she finds

"Tag", "Tag v2", "Chip", "Pill/Status", "Badge (old)", "Label - DO NOT USE", and three more in a page called "WIP". No descriptions. Two look identical.

What happens next

She picks one at random. It turns out to be deprecated. Engineering builds it from scratch because the code version was deleted months ago. The product now has another status tag.

Nothing in that story is about the quality of the components themselves. They may all have been well designed. The problem is findability, and in our experience it's one of the most underrated causes of low adoption. Every minute someone spends confused in your library makes building their own version more tempting.

16.2Organising the design library

A well-organised library feels like a well-organised supermarket: you can guess which aisle something is in, things are labelled clearly, and nothing out of date is left on the shelves. Here's a structure that works for most teams.

Names and descriptions

Remember Rule #3: name things so people can guess them. Use the same component names everywhere (Figma, code, documentation) and avoid version numbers or status in names. "Tag v2 NEW" is a cry for help, not a name. Status belongs in a label or description, not the name.

Most design tools let you add a short description and search keywords to each component. Use them. A good description answers "what is this for?" in one sentence and lists the words someone might search for. "Tag: a short label showing a status or category. Also known as: chip, pill, badge, label." That one line would have saved Meera half a day.

[[prac]] Publish on a rhythm, not on a whim

Publish library updates on the same rhythm as code releases, with the same release notes. When designers get a library update notification, they should know exactly what changed and why. Random, unannounced updates teach people to ignore update notifications, and then they end up working with outdated components.

16.3Documentation that actually gets read

Layer One's ninth rule says it bluntly: docs decide adoption. People use what they can understand in the five minutes before a deadline. If documentation is long, scattered or out of date, people stop reading it and start guessing, or building their own.

The trick isn't writing more. It's writing the same few things for every component, in the same order, so people know exactly where to look. Here's the template we use:

#SectionWhat it answersKeep it to
1SummaryWhat is it, and when should I use it?One or two sentences
2When not to use itWhat should I use instead, and when?Two or three bullet points
3Live examplesWhat does it look like in each option and state?Interactive examples
4AnatomyWhat are the parts called?One labelled diagram
5How to build with itHow do I use it in code and in Figma?Copyable code, settings table, library link
6AccessibilityHow does it work with a keyboard and a screen reader? What must I add?A short checklist
7WritingWhat should the words say?One or two lines, plus examples
8Do's and don'tsWhat does correct and incorrect use look like?Two to four visual pairs
9Status and historyIs it stable? What changed recently?A status label and a short change log

The UK government's GOV.UK Design System is a good public example of documentation done well: every component page follows a consistent structure, explains when not to use it, and shares the research behind it.[[c:govuk-criteria]] Notice also what's not in the template: long essays about design philosophy. Those belong on a separate page for people who want them.

16.4A component's life, from idea to retirement

Components aren't permanent. They're proposed, tried out, settled, and eventually replaced. Giving each stage a clear label tells everyone how much they can rely on a component right now.

The two stages teams most often skip are beta and deprecated, and they're the two that build the most trust. Beta lets you release something before it's perfect without breaking anyone's work when it changes. Deprecated lets you retire something without surprising anyone. Chapter 05 describes the deprecation process in more detail: mark it, give a guide and a notice period, track who's still using it, and only remove it in a major release.

16.5Knowing what's actually being used

You can't look after a library well if you don't know how it's used. Fortunately, both sides of the twins leave a trail.

In design files

Usage and detachments

Design tools can typically show how often each library component is inserted, and how often designers detach it (break the link to customise it). Detachments are gold: they show exactly where a component isn't meeting people's needs.

In code

Imports and versions

A simple script can count which system components each product imports, which version of the package each product uses, and where deprecated components are still in use.

ScenarioWhat the detach numbers revealed
The situation

Ledgerly's system team looks at its design library data for the first time. The alert component is used 900 times, and detached 310 times.

What they find

They look at a sample of the detached copies. Almost all of them added a second button: "Retry" next to "Dismiss". The component only allowed one.

What they do

They add an optional second action, release it in a minor update, and the detach rate drops sharply. No survey or meeting needed; the data told them.

Two cautions. First, remember Rule #8: measure time saved, not just usage. High usage is good, but it isn't the goal in itself. Second, use the data to learn, not to police. If a team detaches a component a lot, the first question is "what does the component fail to do for you?", not "why aren't you following the rules?"

16.6When a team needs something different

Sooner or later, a team will need a component to do something it doesn't do. The marketing team wants a bigger, bolder button for a campaign page. The analytics team needs a table that can freeze three columns. How you respond decides whether the system bends sensibly or breaks into pieces.

There are four common responses, and they're not equally healthy:

ResponseWhat happensWhen it's right
Extend the componentAdd a new option to the core component for everyone.When two or more teams need it and it fits the component's purpose.
Build a local componentThe team builds its own, from system parts, and owns it.When it's specific to one product. It can be promoted later.
Small overrideThe team adjusts one detail of a system component in its own code.Rarely, as a short-term fix, and always reported to the system team.
Copy and modifyThe team copies the system component's code and changes it.Almost never. The copy stops getting fixes and updates, and silently drifts.

The last row is how companies end up with three dropdowns (Chapter 15). It usually happens when the system team is slow to respond, or when "build a local component" isn't presented as a respectable option. Make the healthy paths quick and easy, and copying becomes rare.

The principle behind all of this

The system should make the right thing the easy thing. When teams work around it, treat that as feedback about the system, not a failure of the teams.

Library health checklist

  • Separate libraries for foundations, core and extensions
  • Groups that match how people think, plus a "Start here" page
  • Same names in Figma, code and docs; no versions in names
  • A one-line description and keywords on every component
  • Old versions archived and hidden; no work-in-progress published
  • One documentation template, used for every component
  • A visible life-cycle label on every component
  • Library updates published with release notes, on a rhythm
  • Usage and detach data reviewed monthly
  • Quick, respectable paths for local components

The short version

What to remember from this chapter

  1. Findability is adoption. A tidy, well-named library prevents duplicates before they happen.
  2. Document every component the same way, briefly, and say when not to use it.
  3. Label every component's stage (beta, stable, deprecated) so people know what to rely on.
  4. Use design and code data to learn where components fall short, and make the healthy paths quick and easy.
