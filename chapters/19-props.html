Chapter 19

Props, in depth

Props are the settings on a component: the knobs and switches people use to get the version they need. They look like a small detail, but they decide how easy a component is to use, how consistent the product stays, and how painful it is to change things later.

Read this if

You design or build components, review component proposals, or have ever wondered why some components are a joy to use and others are a puzzle.

What you'll leave with
  1. The different kinds of props, and how each one maps to Figma.
  2. Rules for designing props that are clear, safe and consistent.
  3. How props work under the surface, and how to change them without breaking anyone.

19.1Props are a promise

Go back to the TV remote from Chapter 15. A good remote has a few clearly labelled buttons that do exactly what they say. Nobody has to read a manual to turn the volume up. Now imagine a remote where "volume up" only works if "mode B" is on, and pressing "mute" while "input 2" is selected changes the channel. That's what a component with badly designed props feels like.

Props matter for three reasons. They are the interface designers and engineers use every day, so clarity saves time on every screen. They decide consistency: if a prop lets anyone pick any colour, they will, and the product drifts. And they are a promise: once teams use a prop, changing or removing it breaks their screens, so mistakes in props are expensive to undo.

That's why mature system teams spend more time discussing props than almost anything else. A useful mindset is to treat each prop as something you'll have to support for years. Add one only when you're sure it earns its place.

19.3Designing good props

Here are the rules we use when reviewing props. Each one comes from a mistake we've seen cause real pain.

Prefer one choice over many switches

The most common prop mistake is using several on/off switches for things that are really one choice. If a button has isPrimary, isDanger and isGhost, what happens when someone turns on two at once? Nobody knows. A single variant prop with a list of allowed values makes impossible combinations impossible.

// ✕ Three switches, eight combinations,
//   most of them meaningless
<Button isPrimary isDanger>
  Delete
</Button>
// ✓ One choice, three valid options
<Button variant="danger">
  Delete
</Button>

Use the same names everywhere

If buttons use variant, badges shouldn't use type and alerts shouldn't use kind. If buttons use size="sm", inputs shouldn't use size="small". Write down a short list of standard prop names (variant, size, tone, disabled, loading, label, onChange…) and use them across the whole library. People then learn the library once, not component by component.

Make the default the right answer

Whatever a prop is set to when nobody sets it should be the most common, safest choice. A button should default to the medium size and the secondary variant, so the "big orange button" is a deliberate decision, not an accident. A text field should default to having a visible label, not to hiding it.

Don't let props bypass the system

Props like color="#FF3300" or padding={13} let anyone escape the foundations, and someone always will. Props should offer choices from the system (tone="critical", size="lg"), never raw values.

Only require what's essential

A component should work with as few props as possible. A button needs a label and something to do when clicked; everything else should have a sensible default. Every required prop is something someone will forget.

19.4How props actually work

You don't need to be an engineer to understand the basic mechanics, and knowing them helps designers and engineers talk about components much more precisely.

Information flows one way

In most modern frameworks, information flows down through props, and news flows up through events. The screen tells the component what to show (via props). When something happens inside the component, like a click or a change, the component tells the screen (via an event prop such as onChange). The screen decides what to do, and if needed, sends new props back down.

This one-way flow is what makes components predictable. Given the same props, a component always looks the same. That's also what makes visual testing (Chapter 15) possible: render each combination of props, take a picture, compare.

Controlled and uncontrolled, again

Chapter 18 introduced the idea that either the screen or the component can keep track of a value. In terms of props, an uncontrolled component takes a defaultValue and looks after itself; a controlled component takes a value plus an event like onValueChange, and the screen stays in charge.[[c:react-controlled]] Good libraries name these consistently across every component that has a value, so engineers only learn the pattern once.

Passing things through

Components should usually pass along standard properties they don't use themselves, such as an ID for testing or an accessibility attribute, to the underlying element. Engineers call this "spreading" props. It means the system doesn't block teams from doing ordinary, legitimate things, without having to add a special prop for every case.

For the twins to stay identical, props need to look the same in both places. Here's how Ledgerly's button lines up.

Notice two small differences that are agreed and documented: Figma shows the icon as two properties (a switch and a choice of icon), while code uses one; and Figma treats "disabled" as a visual state, while code treats it as a switch. Differences like this are fine as long as they're written down. What causes trouble is differences nobody decided.

This table is also the right format for documentation. Every component's documentation page should list its props with the same five columns: name, type, default, the Figma equivalent and a plain-language purpose. Many teams generate the first three columns automatically from the code, so they're never out of date, and write the last two by hand.

19.6Changing props without breaking anyone

Props are promises, so changing them needs care. Here's how each kind of change should be handled, using the version-number rules from Chapter 05.

ChangeRelease typeHow to do it safely
Add a new optional propMinorGive it a default that keeps today's behaviour. Nobody notices unless they want it.
Add a new value to a variantMinorAs above. Update Figma at the same time.
Change a default valueMajorEveryone relying on the old default sees a change. Announce it, with screenshots.
Rename a propMajor (eventually)Accept both names for a while, warn when the old one is used, provide an automatic fix, remove the old name in the next major release.
Remove a prop or valueMajorDeprecate first, track usage, give a notice period, then remove.
ScenarioRenaming "kind" to "variant" across 600 buttons
The situation

Ledgerly's early button used kind. Every other component uses variant. The inconsistency confuses new engineers.

What they do

Version 4.3 accepts both kind and variant, and shows a gentle warning in development when kind is used. They publish a small script that rewrites kind= to variant= automatically.

The result

Most teams run the script in a few minutes. Usage tracking shows when the old name is gone. Version 5.0 removes kind, and nobody's screen breaks.

19.7Prop patterns to avoid

Finally, here are the prop patterns we most often recommend removing in audits. If you spot these in your library, they're usually signs of a component that's trying to do too much.

Avoid

Raw style props

color, margin, fontSize as free values. They bypass the foundations. Offer named choices instead.

Avoid

Switch explosions

Many booleans that interact. Combine related ones into a single choice.

Avoid

One-team props

A prop added for one screen in one product. It becomes everyone's maintenance burden. Build it locally instead.

Avoid

"Config" objects

A single prop that takes a big bundle of settings. It hides what the component can do and makes changes hard to track.

Avoid

Contradictory props

Props that make no sense together, like loading and disabled with different meanings. Define clearly which wins.

Avoid

Hidden behaviour

A prop whose name doesn't match what it does, like compact that also hides the icon. Names should never surprise.

The short version

What to remember from this chapter

  1. Props are a long-term promise. Add one only when it earns its place.
  2. Use one choice instead of many switches, the same names everywhere, and safe defaults.
  3. Props flow down and events flow up; support both controlled and uncontrolled use.
  4. Match props in Figma and code, document differences, and change props through deprecation and automatic fixes.
