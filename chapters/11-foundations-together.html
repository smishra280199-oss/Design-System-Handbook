How foundations work together

Colour, type, spacing and layout aren't four separate projects. They're one system. The easiest way to see that is to follow a single button from the first decision all the way to the code that ships.

11.2Into the code

This section is mostly for engineers, but it's worth a look even if you don't write code, because it shows the payoff. An automatic build step turns the list of named values into whatever each platform needs. For websites, that's CSS variables. The button's own code then uses only those names. Look closely: there isn't a single colour code or pixel value typed into the button itself.

/* tokens.css: generated automatically, never edited by hand */
:root {
  --color-brand-700: oklch(0.486 0.172 35);
  --color-brand-800: oklch(0.406 0.146 34);
  --color-action-primary-bg:
    var(--color-brand-700);
  --color-action-primary-bg-hover:
    var(--color-brand-800);
  --space-control-inset-x: var(--space-4);
  --size-control-height: 40px;
}
/* dark mode: only the pointers change */
[data-theme="dark"] {
  --color-action-primary-bg:
    var(--color-brand-400);
}
/* compact mode: only the sizes change */
[data-density="compact"] {
  --size-control-height: 32px;
  --space-control-inset-x: var(--space-2);
}
/* button.css: uses names only */
.button {
  height: var(--size-control-height);
  padding-inline: var(--space-control-inset-x);
  gap: var(--space-2);
  border-radius: var(--radius-control);
  font: var(--type-label-md);
}
.button[data-variant="primary"] {
  background: var(--color-action-primary-bg);
  color: var(--color-action-primary-text);
}
.button[data-variant="primary"]:hover {
  background:
    var(--color-action-primary-bg-hover);
}
.button:focus-visible {
  outline: 2px solid var(--color-focus-ring);
  outline-offset: 2px;
}

iPhone and Android apps get the same values, generated from the same source file into their own languages. The source file is the agreement; each platform's components are just different ways of honouring it.

11.3What happens when something changes

The real test of all this work is change. Here's what each common change touches, and, just as importantly, what it doesn't.

The changePaintsJobsComponentsProductsThe work involved
Rebrand with a new colour●○○○Change one starting colour; shades regenerate; check readability; release.
Add dark mode○●○○One new list of pointers; check every pairing; release.
Make secondary text more readable○●○○Change one pointer; every product is fixed when it updates.
Add a compact mode○●◐○New spacing values; check components with fixed internal sizes.
New set of text sizes●◐○◐Values change; products check any layouts that relied on old sizes.
White-label for a customer●○○○Generate a brand family from the customer's colour.

● changes · ◐ worth checking · ○ untouched. These results only hold if components use named values everywhere. A single colour code typed directly into a component breaks the chain for that component.

Part 02 in one sentence

Decide once, name everything, and let components use only the names. Then almost every future change becomes a settings change instead of a rebuild.

11.4Are your foundations ready?

Before you start building components at scale, run through this list. Each item points back to the chapter that explains it.

Colour ch. 07

  • Shade families built in OKLCH, with colour codes generated by a tool
  • Job names for backgrounds, text, borders, icons, actions, status and focus
  • Light and dark lists, with every pairing checked automatically

Typography ch. 08

  • Text styles named by job, saved as bundles
  • Line spacing on the 4px grid; numbers that line up
  • A plan for screen sizes that respects zoom

Spacing ch. 09

  • A 4px-based scale with names that tell you the size
  • Component spacing with compact and comfortable modes
  • Tap targets big enough for fingers

Layout ch. 10

  • Named breakpoints, columns, gutters and margins
  • The app frame and content widths defined
  • Every pattern planned for a 320px screen

Plumbing ch. 06

  • One source file of named values, turned automatically into code and Figma
  • An automatic check against colour codes typed into product code

The short version

What to remember from this chapter

  1. Every visual detail of a component should come from a named value.
  2. Each layer only knows about the one below it, and that's what makes change safe.
  3. Rebrands, dark mode and readability fixes become changes to names, not to components.
  4. With foundations in place, you're ready for components, which is where Part 03 begins.
