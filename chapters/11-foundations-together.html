Chapter 11

How foundations work together

Colour, type, spacing and layout are not four separate deliverables. They are one system, and the best way to see it is to follow a single component from the first decision to the line of code that ships.

Read this if

You want to see the whole architecture in one place, or you need to explain to engineering how foundations become components.

What you'll leave with
  1. One component traced through five layers: decision, token, component, pattern and production.
  2. A clear picture of what changes, and what doesn't, when a foundation changes.
  3. A foundations readiness checklist to close out Part 02.

11.2Into production

The token pipeline compiles the token source into each platform's format. For the web, that's CSS custom properties, which the component consumes. Notice that the component code contains no raw values at all.

/* tokens.css: generated, never hand-edited */
:root {
  --color-brand-700: oklch(0.486 0.172 35);
  --color-brand-800: oklch(0.406 0.146 34);
  --color-action-primary-bg:
    var(--color-brand-700);
  --color-action-primary-bg-hover:
    var(--color-brand-800);
  --space-control-inset-x: var(--space-4);
  --size-control-height: 40px;
}
[data-theme="dark"] {
  --color-action-primary-bg:
    var(--color-brand-400);
}
[data-density="compact"] {
  --size-control-height: 32px;
  --space-control-inset-x: var(--space-2);
}
/* button.css: consumes semantic tokens only */
.button {
  height: var(--size-control-height);
  padding-inline: var(--space-control-inset-x);
  gap: var(--space-2);
  border-radius: var(--radius-control);
  font: var(--type-label-md);
}
.button[data-variant="primary"] {
  background: var(--color-action-primary-bg);
  color: var(--color-action-primary-text);
}
.button[data-variant="primary"]:hover {
  background:
    var(--color-action-primary-bg-hover);
}
.button:focus-visible {
  outline: 2px solid var(--color-focus-ring);
  outline-offset: 2px;
}

Native platforms receive the same tokens as Swift and Kotlin constants from the same source file. The token source is the contract; each platform's components are implementations of it.

11.3When a foundation changes

The real test of the architecture is change. For each kind of change, here is which layers are touched, and how many are not.

ChangePrimitivesSemanticComponentsProductsEffort
Rebrand: new brand hue●○○○Change one seed; ramps regenerate; validate contrast; release.
Add dark theme○●○○One new semantic mapping; validate pairings; release.
Fix secondary-text contrast○●○○One reference change; every product fixed on upgrade.
Add compact density○●◐○Density mapping; check components with fixed internal sizes.
New type scale●◐○◐Values change; products check layouts that depended on old sizes.
White-label for a customer●○○○Generate a brand tier from the customer's seed at runtime or build time.

● changed · ◐ may need review · ○ untouched. These outcomes hold only if components consume semantic tokens exclusively. A single hard-coded hex in a component breaks the chain for that component.

The whole of Part 02 in one sentence

Decide once in OKLCH, on a 4px grid, in a named type scale; encode the decisions as primitive and semantic tokens; let components consume only semantic tokens. Then every future change is a configuration change.

11.4Foundations readiness checklist

Before building components at scale, confirm the foundations are ready. Each item links back to the chapter that explains it.

Colour ch. 07

  • OKLCH ramps on a fixed lightness curve, hex fallbacks generated
  • Semantic colour tokens for bg, surface, border, text, icon, action, feedback, focus
  • Light and dark mappings with every pairing contrast-tested in CI

Typography ch. 08

  • Role-based scale (display, heading, body, label, caption) as composite tokens
  • Line-heights on the 4px grid; tabular numerals available
  • Responsive strategy that respects zoom and text-spacing overrides

Spacing ch. 09

  • 4px-based scale with guessable token names
  • Semantic component spacing with density modes
  • Target sizes meet WCAG 2.2 AA (24px) and platform touch guidance

Layout ch. 10

  • Named breakpoints, columns, gutters and margins as tokens
  • App shell regions and content-width tokens defined
  • Every pattern planned for 320px reflow

Pipeline ch. 06

  • Single token source (DTCG JSON) compiled to all platforms and the design tool
  • Lint rule against raw values in product code
