Chapter 01

What a design system actually is

Most people picture a design system as a Figma file full of buttons. That's part of it, but only a small part. Let's start from the beginning, with a situation you've probably already lived through.

Read this if

You keep hearing "design system" and you're not sure everyone means the same thing, including you.

What you'll leave with
  1. A plain-English definition you can repeat to anyone.
  2. The difference between a style guide, a UI kit, a component library and a design system.
  3. Why a design system matters more and more as a company grows.

01.1The five-button problem

Picture a product team with five designers. Each of them is working on a different part of the app: one on onboarding, one on billing, one on settings, and so on. None of them is careless. Each one designs a good-looking button for their screens.

A year later, someone counts. The app has five slightly different primary buttons. They're all roughly blue. One has rounded corners, one is a bit taller, one uses a bolder font, one turns a darker blue on hover and another turns lighter. Engineering has built each of them separately, because each designer handed over a different spec.

Nobody decided to have five buttons. It just happened, one reasonable decision at a time.

Now the company changes its brand colour. Somebody has to find all five buttons, in every screen, in design files and in code, and update each one. They'll miss a few. The product will look a little off for months. And the same thing has quietly happened to text styles, form fields, spacing, error messages and icons.

Scenario"Why does our app look like three different companies built it?"
The situation

A growing SaaS company has three product squads. Each squad has its own designer and its own engineers, and each one moves fast.

What goes wrong

Every squad solves the same problems slightly differently: tables, filters, empty screens, error messages. Customers notice. So does the sales team during demos.

What a design system changes

The squads agree on one way to do the common things, build those once, and share them. Each squad spends its time on what makes its part of the product unique.

That, in one story, is why design systems exist. They're not about making things pretty. They're about making sure that many people, working in parallel, end up building one product instead of several that happen to share a logo.

01.2A definition you can actually use

Here's the definition we use with clients. It's deliberately simple:

In one sentence

A design system is a shared set of decisions, reusable parts and working agreements that helps many people build one consistent product, plus the people and process that keep it up to date.

Let's unpack the three ingredients, because most design systems that fail are missing one of them.

01 · Decisions

"What we've agreed"

Which colours we use and for what. How big our text is. How much space goes between things. How we write error messages. The reasons behind the look.

02 · Reusable parts

"What we've built"

Ready-made buttons, inputs, menus and tables, available to designers in their design tool and to engineers in code, plus guidance on how to use them.

03 · Agreements

"How we work together"

Who looks after the system, how people ask for new things, how changes are announced, and what happens when two teams want different things.

Think of it like a restaurant kitchen. The decisions are the recipes. The reusable parts are the prepared ingredients and the tools on the line. The agreements are how the kitchen runs: who orders stock, who changes the menu, how a new dish gets approved. A kitchen with great recipes but no process still serves inconsistent food on a busy night.

When a system is missing one of the three, you can usually spot it:

If you only have…What happens
DecisionsYou have a beautiful PDF of brand rules that nobody opens while they're working.
Reusable partsYou have a library, but it copies whatever inconsistency already existed, because nobody agreed on the rules first.
Decisions and parts, but no agreementsIt works brilliantly for a year. Then it drifts out of date, teams stop trusting it, and they start building their own versions again.

That last row is the most common failure we see. Which is why Layer One's first working rule is:

A design system is an agreement, not a library.Rule #1 — Layer One

01.3Style guide, UI kit, component library, design system

These four terms get used as if they mean the same thing. They don't, and mixing them up leads to real budget mistakes. Let's take them one at a time.

New wordComponentA reusable piece of interface, like a button, a text field or a dropdown, that's built once and used everywhere.

A style guide is a set of written rules about how the brand looks: the logo, colours, fonts, photography style and tone of voice. Think of the brand book your marketing agency handed over. It describes what things should look like, but it doesn't build anything.

A UI kit is a file in a design tool like Figma that contains ready-made pieces of interface (buttons, inputs, icons) that designers can drag into their screens. It makes designers faster and more consistent with each other. But engineers can't use it. They still have to rebuild everything in code by looking at the designs.

A component library is the same idea on the engineering side: buttons, inputs and menus written once in code, which engineers import into the product instead of writing their own. It makes engineers faster. But it often doesn't say when to use which piece, and it's frequently built separately from the designers' UI kit, so the two slowly drift apart.

A design system connects all of this. The designers' parts and the engineers' parts are the same parts, with the same names, built on the same underlying decisions, with guidance on how to use them and a team that keeps everything in sync.

A mistake we see often

"We have a design system" (it's a Figma file)

A team publishes a polished Figma library and announces a design system. Leadership relaxes; the consistency problem is solved. Six months later, engineering has built its own buttons anyway, because nothing they could actually use in code was ever delivered. A UI kit is a perfectly good first step. Just call it a UI kit, so nobody plans as if the code side is covered.

Which one do you have today?

Try this quick check. Every "no" shows you where your current setup stops.

  • Our colours, text sizes and spacing values have names (like "primary-blue" or "space-16"), not just hex codes copied around.
  • Engineers import buttons and inputs from a shared package instead of rebuilding them for each feature.
  • A designer and an engineer would use the same name for the same thing.
  • There's written guidance on when to use each piece, not just what it looks like.
  • Someone is responsible for keeping it up to date, and it's part of their actual job.
  • When something changes, people are told, and they can choose when to update.
  • People know how to ask for something new or suggest a change.

Seven yeses: you're running a design system. One to three: you have a UI kit or a component library, which is a fine place to be, as long as it's a deliberate stage and not where things got stuck.

01.4What's inside a complete design system

Now let's open the box. A complete design system has a few layers that stack on top of each other, plus some things that run through all of them. The important idea is that each layer is built from the one below it. That's what lets a change at the bottom ripple safely all the way up.

New wordDesign tokenA design decision with a name, like "primary-blue = #1C75D6". Design tools and code both read from the same list, so they always match.

Two of these layers deserve a plain-English introduction, because you'll meet them throughout the book.

Foundations are the basic visual decisions that everything else inherits: your colours, your text sizes, how much space goes between things, how pages are laid out. Change a foundation and you change everything built on it. Part 02 of this book is all about getting them right.

Tokens are how those decisions get written down so that both designers and engineers can use them. Instead of a designer writing "#1C75D6" on a spec and an engineer copying it into code (and maybe mistyping it), the colour gets a name, like color-primary. Design tools and code both read the value from the same place. If the colour ever changes, it changes in one place, and everywhere that uses the name updates.

The idea of building interfaces from small parts up to large ones was popularised by Brad Frost's Atomic Design,[[c:frost-atomic]] and the term "design tokens" came out of Salesforce's design system team.[[c:slds-tokens]] In October 2025 an industry working group published the first stable, shared standard for how tokens should be written,[[c:dtcg-announce]] which tells you how mainstream the idea has become.

Complete doesn't mean big

A startup's complete design system might be a one-page list of principles, about a hundred tokens and fifteen components. It still has every layer, just a small amount of each. Completeness is about the layers being connected, not about how much is in them.

01.5How it connects design, engineering, product and business

Here's something that surprises most people: the biggest benefit of a design system isn't the components. It's that everyone ends up speaking the same language.

Without a system, a designer says "the blue button", a product manager says "the main CTA", and an engineer writes code for "btn-submit-v2". They're all talking about the same thing, and every handover is a small act of translation. Translations go wrong. With a system, there's one "primary button". The designer drags it in, the engineer types <Button variant="primary">, and both get exactly the same thing.

Here's what that looks like day to day, before and after:

WhoWithout a systemWith a working system
DesignersRedesign the same table, form and empty screen on every project. Spend hours writing handover specs.Start from known parts and spend their energy on the parts of the problem that are genuinely new.
EngineersBuild "yet another" dropdown. Fix the same keyboard bug in five places.Import a tested dropdown. Fix a bug once, and the fix reaches every screen on the next update.
Product managersEstimates swing wildly because nobody knows how much UI work is hiding in a feature.UI work is predictable, so conversations are about what the feature does, not how many pixels of padding it has.
The businessA rebrand takes quarters. Accessibility problems come back in every audit.Brand and accessibility changes are made in one place and rolled out.

01.6Why it matters more as you grow

A two-person team doesn't need a design system to stay consistent. They sit next to each other. So why does it suddenly become essential at thirty, sixty or three hundred people? Two simple reasons, and neither needs any industry statistics to understand.

Reason one: the number of conversations explodes

If every team that makes UI decisions has to stay in sync with every other team, the number of "have you talked to them?" conversations grows much faster than the number of teams. Four teams have six pairs that need to stay aligned. Sixteen teams have 120. This is the same arithmetic Fred Brooks described decades ago for software teams.[[c:brooks]] If instead every team stays in sync with one shared system, sixteen teams need sixteen relationships, not 120.

Reason two: every change costs more

Remember the five buttons? Without a system, changing the brand colour means hunting down every place it was typed by hand: roughly products × platforms × places it appears. With a system, you change one value and release an update. The same goes for adding dark mode, fixing a contrast problem or refreshing your typography.

That's why the payoff of a design system usually shows up at the second product, the second platform or the first rebrand, not when the first button is built. At CARS24, for example, the work Layer One's founder led put more than ten products in three countries onto one shared colour and token system.[[c:layerone]] Without a shared layer of named decisions, that kind of change would mean editing each product by hand.

[[prac]] A simple test

Judge a design system by what it makes cheap

A good system makes the everyday thing fast (building a normal screen) and the scary thing cheap (changing a decision everywhere at once). If yours does neither, it's a catalogue, not a system.

Ten words you'll meet in this book

FoundationsThe basic visual decisions everything inherits: colour, text, spacing and layout.
TokenA design decision with a name, shared by design tools and code (space-16 = 16px).
ComponentA reusable piece of interface: a button, an input, a dialog.
VariantAn approved version of a component, like a primary or a secondary button.
PatternA proven way to solve a common problem using several components, such as how to show "no results found".
ThemeA complete set of values that changes the look everywhere at once, like dark mode or another brand.
LibraryThe place components live: a Figma library for designers, a code package for engineers.
AdoptionHow much of the real, shipped product is actually built with the system.
ContributionWhen someone outside the system team adds or improves something in the system.
ReleaseA new version of the system that teams can update to, with notes on what changed.

The short version

What to remember from this chapter

  1. Inconsistency doesn't come from carelessness. It comes from many good people making reasonable decisions separately.
  2. A design system is decisions, reusable parts and working agreements. Missing any one of the three is the most common reason systems fail.
  3. A UI kit helps designers, a component library helps engineers, and a design system connects the two with shared names and a way to change.
  4. The value grows with size: more teams, more platforms and more change all make a shared system more valuable.
