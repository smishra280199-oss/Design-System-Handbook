Chapter 01

What a design system actually is

A design system is not a Figma file and it is not a component library. It is a shared agreement about how your product gets made, encoded in tools that design and engineering both use, and kept alive by people whose job it is to keep it alive.

Read this if

You have heard "design system" used for five different things in one meeting, or you need to explain to leadership what you are actually proposing to fund.

What you'll leave with
  1. A precise, defensible definition you can put in a strategy document.
  2. The ability to tell a style guide, UI kit, component library and design system apart, and to know which one you have today.
  3. A clear picture of why a system's value grows faster than the organisation using it.

01.1A working definition

The term is used loosely, and the looseness causes real damage. Leadership approves a "design system" thinking it bought consistency. The design team ships a Figma library. Engineering never adopts it. Eighteen months later the product still has nine kinds of button, and everyone concludes design systems don't work.

So we start with a definition precise enough to plan against:

Definition

A design system is the set of shared decisions, reusable assets and working agreements that lets many people build one coherent product, plus the team and process that keep all three current.

Each of the three parts matters, and most failed systems are missing one of them.

01 — Decisions

What we've agreed

Principles, foundations (colour, type, spacing, layout, motion), accessibility targets, content voice. The why behind every asset.

02 — Assets

What we've built

Design tokens, components in the design tool and in code, patterns, templates, icons and the documentation that explains them.

03 — Agreements

How we work

Ownership, contribution, review, versioning, release and deprecation. The rules for how the first two change over time.

Decisions without assets are a PDF nobody opens. Assets without decisions are a library that encodes whatever inconsistency already existed. Decisions and assets without agreements drift out of date within a year. Layer One's first working rule says it plainly:

A design system is an agreement, not a library.Rule #1 — Layer One

A short lineage

Organisations have codified visual decisions for decades, in brand manuals and corporate identity standards. What changed in software was that the decisions had to be executable. Pattern libraries spread through web teams in the early 2010s. Brad Frost's Atomic Design gave teams a shared mental model for composing interfaces from small parts into large ones.[[c:frost-atomic]] Salesforce's design system team popularised the term design tokens for named design decisions that can be compiled into any platform's code.[[c:slds-tokens]] In October 2025 the W3C Design Tokens Community Group published the first stable version of a vendor-neutral format for those tokens.[[c:dtcg-announce]] Design systems have moved from a design-team initiative to shared product infrastructure, and the standards have caught up.

01.2Style guide, UI kit, component library, design system

These four terms are not synonyms. Each is a part of a design system, and each has a ceiling on what it can do on its own.

ArtefactWhat it isLives inPrimary usersWhat it cannot do alone
Style guideWritten rules for the brand and visual language: logo, colour, typography, imagery, voice.PDF, wiki, brand siteBrand, marketing, designersGuarantee that what ships matches. It describes; it doesn't build.
UI kitReusable visual elements in a design tool: styles, components, icons.Figma (or similar)DesignersReach production. Engineers re-implement it by eye, so the kit and the product drift apart.
Component libraryCoded, reusable UI components with an API (props, variants, states).A code package (e.g. npm)EngineersExplain when and why. Without shared foundations it faithfully reproduces existing inconsistency.
Pattern libraryDocumented solutions to recurring problems: forms, empty states, filtering, onboarding.Docs siteDesigners, PMs, engineersEnforce itself. Patterns are guidance that still has to be built from components.
Design systemAll of the above, connected by tokens, with documentation, ownership and a process for change.Design tool, code, docs, and a teamEveryone who builds the productSucceed without adoption. It is only as real as the share of the product built with it.

Common mistake

Calling a Figma library a design system

It is an easy and costly confusion. Leadership believes the consistency problem is solved; engineering, which never received anything it could import, keeps building its own versions. A UI kit is a legitimate and often correct first step (Chapter 02 explains when). Just call it what it is, so nobody budgets as if production is covered.

Which one do you have today?

Answer honestly. Each "no" marks the edge of what you currently have.

  • Our colours, type sizes and spacing values exist as named tokens, not just hex codes in a file.
  • Engineers import components from a shared package rather than rebuilding them per team.
  • The design library and the code library use the same names for the same things.
  • There is written guidance on when to use each component, not just what it looks like.
  • Someone is accountable for the system, and it is in their job description.
  • Changes are versioned and announced; teams can upgrade on purpose.
  • Teams know how to propose a new component or change an existing one.

Seven yeses and you run a design system. One to three, you have a UI kit or component library with ambitions. That's fine, as long as it's a deliberate stage and not a stall.

01.3The anatomy of a complete design system

A complete system has six layers that build on one another, and three capabilities that cut across all of them. Each layer only references the layer below it. That one-directional dependency is what lets a change at the bottom flow safely to the top.

LayerContainsWho decidesChanges how often
Principles3–5 statements that settle trade-offs ("clarity over density", "accessible by default").Design and product leadershipRarely; years
FoundationsColour, typography, spacing, grid, elevation, radius, motion, iconography. The subject of Part 02.System team, with brandRarely; each change is high-impact
TokensNamed, platform-agnostic values: primitive, semantic, component.System teamOccasionally; via versioned releases
ComponentsButtons, inputs, tables, dialogs, each with variants, states, API and a11y behaviour.System team plus contributorsContinuously; minor releases
PatternsCompositions solving a user problem: search and filter, bulk actions, error recovery.System team plus product teamsContinuously
TemplatesPage scaffolds and layouts built from components and patterns.Product teams, curated by systemAs products evolve

A complete system does not mean a large one. A startup's complete system might be one page of principles, 120 tokens and 15 components, and still have all six layers and all three capabilities. Completeness is about connection, not volume.

01.4How a design system connects the whole organisation

The most underrated function of a design system is linguistic. It gives design, engineering and product one vocabulary for the interface. When a designer says "primary button", an engineer types <Button variant="primary">, and both resolve to the token color.action.primary, a whole category of handoff error disappears.

FunctionWithout a systemWith a working system
DesignRe-solves the same table, form and empty state on every project. Specs every pixel in handoff.Assembles known parts and spends time on the problems that are actually new.
EngineeringBuilds a "new" button per team; fixes the same focus bug in five places.Imports tested components; fixes a bug once and ships the fix everywhere.
ProductEstimates swing because UI scope is unknown; design QA becomes a release gate.UI scope is predictable; teams talk about behaviour, not padding.
BusinessA rebrand is a multi-quarter programme; accessibility is a recurring audit finding.Brand and accessibility changes are made at the token layer and released.

01.5Why design systems matter more as products scale

A design system's value is not linear in company size. It compounds, for two reasons you can reason about without any vendor statistics.

Reason one: coordination grows faster than headcount

If every team that makes UI decisions has to stay consistent with every other team, the number of pairwise agreements grows as n(n−1)/2. That is the communication-path arithmetic Fred Brooks described for software teams.[[c:brooks]] Four teams need six agreements. Sixteen teams need 120. If instead each team agrees with one shared system, the number of agreements grows only as n.

Reason two: the cost of change multiplies

Without tokens, changing a brand colour means finding every hard-coded value across every codebase, platform and design file: roughly products × platforms × occurrences. With a token architecture, it means changing one value and releasing. The same applies to an accessibility fix, a new dark theme or a typography refresh. The more surfaces you have, the more each "change once" saves. That's why the clearest returns usually appear at the second product, the second platform or the first rebrand, not at the first component.

This is the kind of problem design systems exist to solve. At CARS24, for example, the work Layer One's founder led put more than ten products in three countries on one colour and token system.[[c:layerone]] That outcome is only practical with a token layer between decisions and code.

Judge a design system by what it makes cheap

Good systems make the common case fast (building a standard screen) and the expensive case cheap (changing a decision everywhere). If yours does neither, it is a catalogue, not a system.

Glossary: the ten terms this playbook uses precisely

FoundationA category of fundamental visual decision: colour, typography, spacing, layout, elevation, motion.
Design tokenA named design decision stored in a platform-agnostic format and compiled into code (space.400 = 16px).
Primitive tokenA raw value with a descriptive name and no usage intent (color.blue.600).
Semantic tokenA token named for its purpose that points to a primitive (color.text.link → color.blue.700).
ComponentA reusable piece of UI with a defined API, variants, states and accessibility behaviour.
VariantA sanctioned alternative form of a component (primary, secondary, destructive).
PatternA reusable solution to a recurring user problem, composed of components.
ThemeA complete mapping of semantic tokens to values (light, dark, a brand).
AdoptionThe share of the shipped product built with the system, measured in code, not in Figma.
ContributionA change to the system proposed or built by someone outside the core team.
