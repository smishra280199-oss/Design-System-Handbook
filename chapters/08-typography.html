Chapter 08

Typography systems

Most of any interface is text. A typography system isn't a font choice and a list of sizes. It is a set of roles, a scale, a rhythm and a set of rules that keep text readable on every screen and every platform.

Read this if

You are choosing a typeface, defining a type scale, or your product's hierarchy feels muddy or inconsistent across screens.

What you'll leave with
  1. A method for building a type scale, from ratio to rounded, grid-aligned values.
  2. A complete, tokenised product type scale you can adapt.
  3. Guidance on how typography should differ across SaaS, enterprise, mobile, desktop and data-heavy products.

08.1Choosing typefaces

For product interfaces, typeface selection is primarily a functional decision. Brand expression matters, but it is secondary to legibility at small sizes and coverage of everything the product needs to display.

System fonts

Platform UI fonts (San Francisco on Apple platforms, Roboto on Android, Segoe UI on Windows) are highly legible, free, cost nothing to load and feel native. They're the right default for many internal and enterprise tools. The trade-off is weaker brand distinctiveness.

How many families?

One family for UI is usually enough. A second (a mono for code and data, or a display face for marketing) is common. A third is rarely justified in product UI. This playbook uses Schibsted Grotesk for everything and JetBrains Mono for values a machine reads.

Variable fonts

A variable font stores a continuous range of a design axis, most commonly weight, in one file.[[c:mdn-variable-fonts]] Instead of choosing between four static weights, the system can use any weight between, say, 400 and 900. For a design system this means one file to load, exact weight tokens (font.weight.semibold = 600), and optical adjustments such as slightly heavier weights in dark mode.

08.2Type scale architecture

A type scale is the limited set of font sizes your product uses. The classical method is a modular scale: start from a base size (usually 16px, the browser default) and multiply by a constant ratio for each step up, divide for each step down.

A pure modular scale is a starting point, not the answer. Product interfaces need several sizes clustered between 12 and 20px (labels, body, small headings), and only a few large sizes. A single ratio rarely provides both. Most mature systems therefore start from a ratio and then adjust by hand, rounding to whole pixels and to the line-height grid. Material 3's type scale, for example, is a curated set of 15 named styles rather than a strict geometric progression.[[c:m3-type]] [[doc]]

Line-height: tighter as text grows

Line-height (leading) should decrease as a ratio as size increases. Body text needs about 1.4–1.6× for comfortable reading; large headings look loose above about 1.2×. Snap every line-height to your spacing grid (4px in this playbook) so text and components align vertically.

Letter-spacing (tracking)

Typefaces are spaced for text sizes. At large sizes, the default spacing looks loose, so display and heading styles usually take slightly negative tracking (around −0.01 to −0.02em). At very small sizes, and in all-caps labels, slightly positive tracking improves legibility. Store tracking in em so it scales with size.

08.3Roles and hierarchy: a complete product scale

Name type styles by role, not by size. "Heading large" survives a redesign; "28px" doesn't. Five role families cover almost every product interface:

Display

Hero numbers, marketing moments, empty-state headlines.

Heading

Page and section titles; the structure of a screen.

Body

Paragraphs, descriptions, table cells, form values.

Label

Buttons, tabs, form labels, navigation. Medium weight.

Caption

Metadata, timestamps, helper text, footnotes.

Hierarchy uses more than size

A common mistake is to create hierarchy with size alone, which inflates the scale. Weight, colour (text.primary vs text.secondary), case and spacing are equally strong signals and cost no new sizes.

08.4Responsive typography

Large display and heading sizes that work on a desktop overwhelm a phone. There are two approaches:

Stepped

Different token values per breakpoint

heading.xl is 28px below 600px wide and 36px above. Simple, predictable, easy to spec in design tools.

Fluid

Interpolate between a minimum and maximum

Size scales smoothly with viewport width using CSS clamp(). Fewer jumps; popularised by tools such as Utopia.[[c:utopia]]

/* heading.xl: 28px at a 360px viewport → 36px at 1280px */
--type-heading-xl-size: clamp(1.75rem, 1.554rem + 0.87vw, 2.25rem);

/* slope     = (36 − 28) ÷ (1280 − 360) = 0.0087  → 0.87vw
   intercept = 28 − 0.0087 × 360  = 24.87px     → 1.554rem */

Common mistake

Fluid type that ignores zoom

Font sizes set purely in viewport units (font-size: 3vw) don't grow when users zoom, which can fail WCAG 2.2 SC 1.4.4 (Resize Text, up to 200%).[[c:wcag22]] [[std]] Always include a rem component in the fluid formula, as above, and only make display and heading sizes fluid. Body text should stay fixed and readable.

Native platforms add their own layer. iOS Dynamic Type and Android's font scaling let users choose larger text system-wide. Apple's guidelines encourage supporting Dynamic Type so text scales with the user's preference.[[c:hig-type]] A design system for native apps should map each type token to the platform's scalable text style rather than to a fixed size.

IBM Carbon formalises a similar split with two type sets: a productive set for dense task-focused product UI and an expressive set for editorial and marketing moments.[[c:carbon-type]] [[doc]] If your product has both a dense app and a marketing surface, consider the same separation rather than one compromise scale.

08.7Typography tokens

Typography uses two token levels. Primitive tokens hold individual values (families, sizes, weights, line-heights, tracking). Composite tokens bundle them into styles by role. The DTCG format defines a composite typography type for exactly this.[[c:dtcg-format]]

// primitives
"font": {
  "family": { "sans": { "$type": "fontFamily", "$value": ["Schibsted Grotesk", "system-ui", "sans-serif"] } },
  "weight": { "semibold": { "$type": "fontWeight", "$value": 600 } }
},
// composite, by role
"type": { "heading": { "lg": {
  "$type": "typography",
  "$value": {
    "fontFamily": "{font.family.sans}", "fontWeight": "{font.weight.semibold}",
    "fontSize": { "value": 28, "unit": "px" }, "lineHeight": 1.29,
    "letterSpacing": { "value": -0.01, "unit": "em" }
  } } } }

Typography checklist

  • One UI family (plus mono if needed), tested at 12–14px
  • Tabular numerals available and used in tables
  • 10–15 styles named by role, not size
  • Line-heights snapped to the 4px grid
  • Tracking defined in em for display and labels
  • Responsive strategy chosen: stepped or fluid (with rem)
  • Layouts survive 200% text resize and text-spacing overrides
  • Reading widths capped at roughly 45–75 characters
  • Native styles mapped to Dynamic Type / font scaling
  • Composite typography tokens in design tool and code
