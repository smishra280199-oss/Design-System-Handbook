Chapter 08

Typography systems

Most of what people look at in your product is text: labels, numbers, headings, messages. A typography system isn't just picking a nice font. It's deciding a small set of text styles, each with a clear job, that stay readable on every screen.

Read this if

You're choosing a font, setting up text sizes, or your screens feel cluttered and it's hard to tell what's important.

What you'll leave with
  1. How to choose a font for a product (not a poster).
  2. A complete, named set of text styles you can adapt.
  3. How text should differ between dashboards, mobile apps, enterprise tools and more.

08.1Choosing a font

When a brand team picks a font, they're usually thinking about a logo, a billboard or a headline. A product font has a harder job. It has to be readable at 12 pixels in a crowded table, show numbers that line up in columns, and work in every language you sell in. So for products, choosing a font is mostly a practical decision. Personality matters, but it comes second.

The "do nothing" option

Every operating system has a built-in interface font: San Francisco on Apple devices, Roboto on Android, Segoe UI on Windows. They're very readable, free, load instantly and feel familiar. For internal tools they're often the best choice. The trade-off is that your product looks less distinctive.

How many fonts?

One for the interface is usually enough. A second, like a monospaced font for codes and IDs or a display font for marketing, is common. A third is rarely needed. This book uses one font for everything, plus a monospaced font for values a computer would read.

Variable fonts: one file, every weight

New wordVariable fontA single font file that can produce any weight (and sometimes width) in a range, instead of separate files for each.

Traditionally, regular, medium and bold were separate font files. A variable font stores a whole range of weights in one file.[[c:mdn-variable-fonts]] For a design system that means fewer files to load and exact weights to choose from. Systems still name a small set of weights, so "any weight" doesn't turn into "every weight".

08.2Text sizes that work together

New wordType scaleThe short, fixed list of text sizes a product uses, like 12, 14, 16, 18, 22, 28 and 36 pixels.

If anyone can pick any text size, you end up with 13, 14, 14.5, 15 and 16 pixels all over the product, and nothing quite looks related. A type scale fixes this: a short list of sizes that everyone chooses from.

A classic way to create one is to start from a base size (usually 16 pixels, the browser's default) and multiply by the same number each step up. That number is called the ratio. A small ratio gives you lots of sizes close together; a large ratio jumps quickly to big headlines.

In practice, a pure mathematical scale is a starting point, not the answer. Apps need several sizes clustered between 12 and 20 pixels (labels, body text, small headings) and only a few large ones. So most mature systems start from a ratio, then adjust by hand and round to whole numbers. Google's Material Design 3, for example, uses a hand-tuned set of 15 named styles rather than a strict formula.[[c:m3-type]] [[doc]]

Line spacing: tighter as text gets bigger

The space between lines (designers call it line-height or leading) should get proportionally tighter as text gets bigger. Body text reads comfortably at about 1.4 to 1.6 times its size. Big headlines look loose and disconnected above about 1.2. We also round every line-height to a multiple of 4 pixels, so text lines up neatly with everything else on the page (Chapter 09 explains why 4).

Letter spacing

Fonts are spaced for reading sizes. Blown up to headline size, the gaps between letters start to look too wide, so big headings usually get slightly tighter letter spacing. Very small text and ALL-CAPS labels go the other way and get slightly looser spacing, which makes them easier to read.

08.3Naming text by its job

Just like colours, text styles should be named by what they're for, not by their size. "Heading large" survives a redesign; "28px" doesn't. Five families of text cover almost every product:

Display

Big numbers and headlines: a dashboard total, a welcome message.

Heading

Page and section titles: the structure of a screen.

Body

Paragraphs, descriptions, table cells, form values.

Label

Buttons, tabs, form labels, menu items. Slightly bolder.

Caption

Timestamps, helper text, small print.

Making things stand out takes more than size

A common mistake is trying to show importance with size alone. You end up with a dozen sizes and a page that still feels flat. Weight (bold or regular), colour (dark or grey), capital letters and space around text are just as effective, and they don't add new sizes.

08.4Text on different screen sizes

A 36-pixel heading looks great on a laptop and takes up half the screen on a phone. There are two ways to handle this.

Stepped

Different sizes per screen size

"Heading XL" is 28px on phones and 36px on larger screens. Simple, predictable, and easy to show in design files.

Fluid

Sizes that grow smoothly

Text grows gradually between a minimum and a maximum as the screen widens, using a CSS feature called clamp(). Tools like Utopia popularised this.[[c:utopia]]

For the engineers reading, here's what a fluid heading looks like in code, with the maths spelled out:

/* Heading XL: 28px on a 360px-wide phone → 36px on a 1280px-wide laptop */
--type-heading-xl-size: clamp(1.75rem, 1.554rem + 0.87vw, 2.25rem);

/* growth  = (36 − 28) ÷ (1280 − 360) = 0.0087 → 0.87vw
   start   = 28 − 0.0087 × 360       = 24.87px → 1.554rem */

A mistake we see often

Fluid text that ignores zoom

If text size is based only on screen width, it won't get bigger when someone zooms in, which can fail the accessibility requirement that text can be enlarged to 200%.[[c:wcag22]] [[std]] Always include a fixed part (the rem part above) in the formula, and only make headings fluid. Keep body text at a steady, readable size.

On phones and tablets, there's another layer. iPhone and Android both let people choose a larger text size for every app on their device. Apple's guidelines encourage apps to support this, which it calls Dynamic Type.[[c:hig-type]] A design system for mobile apps should connect each of its text styles to the platform's built-in, adjustable text styles rather than fixing sizes in place.

08.5Readable for everyone

Accessibility for text isn't a separate project. Most of it is decided by the type system. Here's what to build in from the start:

IBM's Carbon formalises a similar idea with two sets of text styles: a "productive" set for dense, task-focused screens, and an "expressive" set for marketing and storytelling pages.[[c:carbon-type]] [[doc]] If your company has both a busy app and a marketing site, consider two sets rather than one compromise.

08.7Turning text styles into tokens

Text uses two levels of named values, just like colour. The first level names individual values: the font family, each weight, each size. The second level bundles them into complete styles named by job, like "heading large". The shared token format has a built-in "typography" type for exactly this kind of bundle.[[c:dtcg-format]] Here's what that looks like:

// individual values
"font": {
  "family": { "sans": { "$type": "fontFamily", "$value": ["Schibsted Grotesk", "system-ui", "sans-serif"] } },
  "weight": { "semibold": { "$type": "fontWeight", "$value": 600 } }
},
// a complete style, named by its job
"type": { "heading": { "lg": {
  "$type": "typography",
  "$value": {
    "fontFamily": "{font.family.sans}", "fontWeight": "{font.weight.semibold}",
    "fontSize": { "value": 28, "unit": "px" }, "lineHeight": 1.29,
    "letterSpacing": { "value": -0.01, "unit": "em" }
  } } } }

Typography checklist

  • One interface font (plus a monospaced one if needed), tested at small sizes
  • Numbers that line up in tables
  • 10–15 styles named by job, not size
  • Line spacing rounded to multiples of 4px
  • Letter spacing set for headings and labels
  • A plan for screen sizes: stepped or fluid (with zoom support)
  • Layouts survive 200% zoom and readers' own spacing
  • Long text kept to about 45–75 characters per line
  • Mobile styles connected to users' text-size settings
  • The same named styles in Figma and in code

The short version

What to remember from this chapter

  1. Choose a product font for readability at small sizes, aligned numbers and language support first.
  2. Use a short, fixed list of sizes, with line spacing that gets tighter as text gets bigger.
  3. Name text styles by their job, and show importance with weight, colour and space as well as size.
  4. Build accessibility into the styles themselves: contrast, zoom and flexible boxes.
