Chapter 14

Designing a component that lasts

A component in a design system is used in hundreds of places by people you'll never meet, with content you'll never see. Designing one is less about making it look good in a mock-up and more about predicting everything that will happen to it in real life.

Read this if

You design components, review them, or keep finding that system components break when real content and real people get hold of them.

What you'll leave with
  1. A process that starts from real use, not from a blank canvas.
  2. Checklists for states, edge cases and accessibility.
  3. A clear "ready to build" standard for handing a component to engineering.

14.1Start from real use, not a blank canvas

When designers start a new component, the instinct is to open a blank frame and design the ideal version. For a system component, that's the wrong starting point. The right one is the inventory from Chapter 13: every version of this component that already exists, and every situation it's used in.

ScenarioThe alert that looked perfect until it met real messages
The situation

A designer creates a beautiful alert component. In the mock-up, every message is one short line: "Changes saved."

What goes wrong

In the real product, messages include "Your payment of ₹1,24,000 to Acme Supplies could not be processed because the bank declined the transaction. Try another payment method." The alert wraps onto four lines, the icon floats in the middle, and the close button overlaps the text.

What would have helped

Collecting twenty real alert messages from the product before designing, and testing the design with the longest, shortest and strangest ones.

So before you design, gather the evidence:

  • Every existing version of the component, from the inventory, and what each one was trying to do.
  • Real content: actual labels, messages and data from the product, including the longest and the oddest.
  • Where it's used: in a table, in a dialog, on a phone, in a dense dashboard, in a marketing page.
  • What teams have asked for: open requests and complaints about the current versions.
  • How others do it: look at how mature public systems handle the same component, for ideas and pitfalls.

14.2Design every state and every edge

In Chapter 12 we saw a text field in eight states. Most components have more situations than people expect, and the ones you forget are the ones that end up looking broken in production. Here's a checklist we use for every component.

SituationQuestions to answer
Interaction statesDefault, hover, pressed, keyboard focus, selected, disabled, read-only. What does each look like?
Data statesEmpty, loading, partly loaded, error, success. What shows while we wait? What if there's nothing to show?
Too much contentA very long name, a huge number, 300 items in a list. Does it wrap, cut off with "…", or scroll?
Too little contentA one-character name, a single item. Does it still look intentional?
Other languagesSome languages need much more space than English for the same message; some read right to left. Does the layout survive?
Screen sizesWhat happens on a phone? In a narrow side panel? On a very wide screen?
Bigger text and zoomIf someone sets their text size larger, or zooms to 200%, does anything get cut off?
CombinationsError and disabled? Loading and selected? Which combinations are possible, and which should be prevented?

[[prac]] The "stress test" frame

Keep a page in your design file next to every component called "stress test". Put the component in it with the longest real content, the shortest, an empty state, an error, a translated version and a phone-width version. Review that page, not the pretty one. It takes an hour and saves weeks of bug reports.

14.3Accessible from the start

Layer One's fifth rule is accessible by default, not by audit. For components, this matters even more than anywhere else, because every accessibility problem in a component is copied into every screen that uses it. The good news is that the reverse is also true: get a component right once, and every screen gets it right.

Accessibility can sound intimidating, so here it is in plain terms. For each component, make sure that:

Everyone can…Which meansSource
See itText has enough contrast (4.5:1), and so do the edges of fields and buttons (3:1). Information never relies on colour alone.[[std]] WCAG 1.4.3, 1.4.11, 1.4.1[[c:wcag22]]
Use it with a keyboardEvery action can be reached with Tab and triggered with Enter or Space. Menus and dialogs follow the standard keyboard patterns.[[std]] WCAG 2.1.1; ARIA patterns[[c:aria-apg]]
See where they areA clear focus outline appears when moving with the keyboard.[[std]] WCAG 2.4.7
Hear what it isScreen readers announce what it is ("button"), its name ("Send invoice") and its state ("expanded", "selected").[[std]] WCAG 4.1.2
Hit itClick and tap targets are at least 24 × 24px, and 44–48 on touchscreens.[[std]] WCAG 2.5.8[[c:wcag-target]]
Understand errorsError messages say what's wrong and how to fix it, and are connected to the field they describe.[[std]] WCAG 3.3.1, 3.3.3
Avoid discomfortAnimations respect the "reduce motion" setting on people's devices.[[prac]]

For complex interactive components like menus, tabs, dialogs and comboboxes, don't invent the keyboard behaviour. The W3C's ARIA Authoring Practices Guide documents the expected behaviour for each of these patterns, including which keys do what, and it's the reference most accessible component libraries follow.[[c:aria-apg]] [[doc]]

ScenarioThe dialog you couldn't escape
The situation

A team builds its own confirmation dialog. It looks great and works perfectly with a mouse.

What goes wrong

Keyboard users press Tab and the focus goes behind the dialog into the page. Escape doesn't close it. Screen readers don't announce it. It ships in 40 places before anyone notices.

The system fix

One dialog component with focus kept inside, Escape to close, focus returned afterwards, and a proper announcement. Fixed once; every one of the 40 dialogs inherits it.

14.4The words are part of the component

A button isn't finished when its colour and padding are decided. What it says matters just as much. Good systems include writing guidance alongside each component, because consistent words are as important as consistent pixels.

ComponentInstead of…Write…Why
Button"Submit", "OK", "Yes""Send invoice", "Delete 3 files"Say what will happen. People often read only the button.
Error message"Invalid input""Enter a date after 1 January 2026"Say what's wrong and how to fix it.
Empty state"No data""No invoices yet. Create your first invoice to get paid faster."Explain why it's empty and what to do next.
Confirmation"Are you sure?""Delete this customer? Their 12 invoices will also be deleted."Spell out the consequence.
LabelPlaceholder text onlyA visible label above the fieldPlaceholders disappear when you type, and are often low-contrast.

You don't need a full content style guide on day one. Start with one or two sentences of writing guidance on each component's documentation page, plus a handful of real examples. Those few lines will do more for consistency than a 40-page tone-of-voice document nobody reads.

14.5"Ready to build": what a finished design includes

When is a component design ready to hand to engineering? Many disagreements between designers and engineers come down to different answers to that question. Agree on one checklist, and use it every time.

The design is ready when it has…

  • An anatomy diagram with every part named
  • Every option (types, sizes) and which combinations are allowed
  • Every state, including empty, loading and error
  • The stress test: long, short, translated and phone versions
  • Named values only: every colour, size and space is a token, not a number

…and also

  • Behaviour notes: what happens on click, keyboard use and resize
  • Accessibility notes: keyboard pattern, focus, what screen readers announce
  • Writing guidance: one or two lines plus examples
  • When to use it, and when to use something else instead
  • An engineer's review of the design before building starts

That last item is the most important. Bring an engineer in while the component is being designed, not after. A ten-minute conversation ("can the menu really open upwards when there's no space below?") prevents a week of rework. The best system teams pair a designer and an engineer on every component from the first sketch.

14.6Test it in the real product

A component isn't proven until it's been used in a real product by a team that didn't design it. That's why pilots matter so much (see Chapter 05). Before calling a new component stable, put it into one or two live product screens and watch what happens.

  1. Release it as "beta"

    Label it clearly as new and still settling, so teams know it might change slightly.

  2. Use it in a pilot

    One real product team uses it in real work, with a direct line to the system team.

  3. Watch for workarounds

    If the team detaches it in Figma, overrides it in code or asks "how do I make it do X?", that's design feedback.

  4. Adjust, then promote to "stable"

    Fix what the pilot revealed, then announce it as stable and ready for everyone.

[[prac]] The review questions we always ask

Can a new designer understand when to use this in under a minute? Does it work with only a keyboard? What happens with the longest real content we've ever seen? Which existing versions will this replace, and how will teams switch? If any answer is "not sure", it isn't ready yet.

The short version

What to remember from this chapter

  1. Start from real examples and real content, not a blank canvas.
  2. Design every state and stress-test every edge before handing over.
  3. Build accessibility into the component, and every screen inherits it.
  4. Agree one "ready to build" checklist, involve engineers early, and prove components in a pilot before calling them stable.
