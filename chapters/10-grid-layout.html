Chapter 10

Grid and layout systems

A layout system decides where things go on every screen size before anyone designs a single page. Done well, nobody notices it. Done badly, every screen breaks in its own special way on someone's phone.

Read this if

You're deciding how your product adapts to different screens, designing a dashboard, or your pages look fine on your laptop and fall apart elsewhere.

What you'll leave with
  1. The parts of a layout grid, in plain language, with real numbers.
  2. How to choose the screen widths where your layout changes.
  3. A practical way to lay out dashboards and complex business software.

10.1What a grid is

Look at a newspaper. The text sits in columns, photos span one, two or three of them, and everything lines up even though dozens of people worked on the page. That's a grid at work. On screens, grids do the same job: they make things line up without anyone measuring.

A layout grid splits the width of the screen into columns, with fixed gaps between them called gutters. Around the outside there are margins, and the whole thing sits inside a container. Content spans whole columns (plus the gutters between them), so edges line up across the page.

PartWhat it isRule of thumb
ColumnsThe vertical strips content lines up to.4 on phones, 8 on tablets, 12 on laptops and desktops.
GuttersThe fixed gaps between columns.Use a value from the spacing scale (16–24px). Gutters stay fixed; columns stretch.
MarginsThe space between the grid and the edge of the screen.Grows with screen size: 16px on phones, up to 32–80px on big screens.
ContainerThe box the grid lives in, sometimes with a maximum width.Cap the width of reading pages (around 1200–1440px); let busy apps use the full width.

10.2Where the layout changes: breakpoints

New wordBreakpointA screen width at which the layout changes, for example from one column to two.

A breakpoint is a screen width where your layout rearranges itself: the side menu tucks away, two columns become one, and so on. The trick is to set breakpoints where your layout needs to change, guided by common types of device, rather than chasing specific phone models, which change every year. Here's how two of the most mature design systems do it:

Two respected systems, two different sets of numbers, and both work well. The lesson isn't to copy either. Pick four or five breakpoints, give them names rather than device names ("medium", not "iPad"), and share them as named values so design and code agree. Ledgerly uses Material's size classes with 4, 8 and 12 columns.

10.3Stretchy, fixed, or both

Fluid

Stretches to fill the screen

Uses all the space. Great for busy apps, but lines of text get uncomfortably long on wide screens.

Fixed

Always the same width

Predictable and easy to design, but wastes space on big screens and needs separate layouts for small ones.

Both (recommended)

Stretches, up to a limit

Columns stretch with the screen until a maximum width. Reading pages use the limit; busy apps can skip it.

How wide should content be?

The grid decides where things can go. Separately, you should decide how wide some things should be. Paragraphs are easiest to read at around 45–75 characters per line,[[c:bringhurst]] so body text should rarely stretch across all 12 columns of a big screen. Forms work best narrow, too. Set these widths as their own named values:

Named widthValueUsed for
width-prose68 charactersArticles, help pages, long descriptions
width-form560pxSingle-column forms and settings
width-dialog560pxStandard pop-up dialogs
width-page1440pxMaximum width for reading and marketing pages
width-appnoneBusy app screens that use the full width

10.4Laying out a dashboard

Most business software isn't really a set of pages on a grid. It's a frame (a top bar and a side menu that stay put) around a content area that changes. If the design system defines the frame once, every team stops reinventing it, and every product feels like part of the same family.

Four dashboard rules that always help

  1. Most important thing at the top left

    In left-to-right languages, people start reading at the top left. Put the number that answers "is everything OK?" there.

  2. Cards in a row share a height

    Matching heights keep the grid visible and make side-by-side comparison easy.

  3. A short list of widths

    Allow cards to span 3, 4, 6, 8, 9 or 12 columns. Avoid 5 and 7, which create edges that don't line up with anything.

  4. Flip for right-to-left languages

    Build with "start" and "end" rather than "left" and "right", so Arabic and Hebrew layouts mirror correctly from the same design.

10.5Phones, desktops and what lines up with what

A phone layout isn't a shrunken desktop

On a phone, the side menu becomes a bottom bar or a slide-out drawer, side-by-side panels become separate screens with a back button, and wide tables become lists or cards. Decide these changes once, as patterns, and every product gets them for free.

Big things line up to columns; small things line up to each other

Page sections and cards line up to grid columns. Inside a card, elements line up with each other using spacing values. A button doesn't need to snap to a column. Trying to grid everything makes components rigid and awkward.

The narrow-screen rule

WCAG 2.2 requires content to fit a screen 320 pixels wide without scrolling sideways, except for things that genuinely need two dimensions, like data tables, maps and diagrams.[[c:wcag-reflow]] [[std]] Plan the 320px version of every pattern. Only ever scroll sideways inside a table, never the whole page.

10.6Layouts for complex business software

Big enterprise tools push past a simple page grid. Think of an email app with a folder list, a message list and a reading pane side by side, or a CRM where you resize panels to fit your work. Your layout system needs words and rules for these too:

Several panes side by side

List and detail views that sit side by side on big screens and become separate screens on small ones. Material documents these as standard layouts.[[c:m3-layout]]

Panels you can resize or fold

People who use a tool all day expect to resize panels. Set minimum and maximum widths as named values, and remember each person's choice.

Components that fit their space

A component in a narrow side panel should adapt to its panel, not the whole screen. A newer CSS feature called container queries makes this possible.

Headers that stay put

Table headers that stay visible while scrolling, first columns that stay fixed, and sideways scrolling inside tables keep people oriented in large data sets.

Layout values, written down

Like everything else, layout decisions become named values that design and code share:

"breakpoint": { "medium": "600px", "expanded": "840px", "large": "1200px", "xlarge": "1600px" },
"grid":       { "columns": { "compact": 4, "medium": 8, "expanded": 12 },
                "gutter": "{space.4}", "margin": { "compact": "{space.4}", "expanded": "{space.6}" } },
"layout":     { "sidebar": { "width": "240px", "folded": "64px" }, "topbar": { "height": "48px" },
                "width": { "prose": "68ch", "form": "560px", "page": "1440px" } }

A note for engineers: CSS variables can't be used inside media query conditions, so breakpoint values are turned into fixed constants (in Sass or JavaScript, for example) rather than CSS variables.

Layout checklist

  • 4–5 named breakpoints, shared by design and code
  • Columns for each (for example 4 / 8 / 12)
  • Gutters and margins taken from the spacing scale
  • Stretchy layouts with a maximum width for reading pages
  • Named widths for text, forms and dialogs
  • The app frame (top bar, side menu) defined once
  • Phone versions of each pattern decided once
  • Everything works at 320px wide (tables excepted)
  • "Start" and "end" instead of "left" and "right"
  • Components that adapt to the panel they're in

The short version

What to remember from this chapter

  1. A grid is columns, gutters, margins and a container. It makes things line up without measuring.
  2. Choose a few named breakpoints where your layout genuinely needs to change.
  3. Stretch layouts to a limit, and cap the width of text and forms for readability.
  4. Define the app frame and the phone versions of patterns once, so every team inherits them.
