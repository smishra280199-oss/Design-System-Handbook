Chapter 10

Grid and layout systems

Grids are how a product decides where things go on every screen size before anyone designs a single screen. In modern products, layout is less about a column grid on a page and more about regions, containers and how they adapt.

Read this if

You are defining breakpoints, designing an app shell or dashboard, or your screens break in different ways on every device.

What you'll leave with
  1. The anatomy of a grid (columns, gutters, margins, containers) and the numbers for each.
  2. A breakpoint system grounded in published systems.
  3. A layout model for SaaS dashboards and complex enterprise applications.

10.1Grid fundamentals

A layout grid divides the available width into columns separated by gutters, inside margins, within a container. Content spans whole columns (and the gutters between them), so edges align across the screen without anyone measuring.

PartDefinitionGuidance
ColumnsVertical divisions content snaps to.4 on phones, 8 on tablets, 12 on desktop is the common pattern.
GuttersFixed space between columns.Use spacing tokens (16–24px). Gutters stay fixed; columns flex.
MarginsSpace between the grid and the screen edge.Grow with screen size: 16px on phones up to 32–80px on large screens.
ContainerThe box the grid lives in; may have a maximum width.Cap reading layouts (~1200–1440px); let data-dense apps go full width.

10.2Breakpoints and responsive grids

Breakpoints are the widths at which the layout changes structure. Set them where your layout needs to change, informed by common device classes, rather than by specific devices, which change every year.

Two mature systems, two different sets of numbers, and both work. The lesson is not to copy either set. Pick a small number of breakpoints (four or five), give them names rather than device labels, and tokenise them so design and code agree. Ledgerly uses Material's classes with 4, 8 and 12 columns.

10.3Fluid, fixed and hybrid layouts

Fluid

Columns stretch with the viewport

Uses all available space. Right for data-dense apps, but long lines of text become unreadable on wide screens.

Fixed

Container has a set width

Predictable, easy to design, but wastes space on large screens and needs separate layouts for small ones.

Hybrid (recommended)

Fluid up to a maximum

Columns flex between breakpoints; the container caps at a maximum width for reading layouts. Apps can opt out of the cap.

Content width

Grids decide where things can go; content width decides how wide reading content should be. Line length for prose is best kept around 45–75 characters,[[c:bringhurst]] which means body text should rarely span all 12 columns of a wide screen. Set content-width tokens independently of the grid:

TokenValueUsed for
layout.width.prose68chArticles, help content, long descriptions
layout.width.form560pxSingle-column forms and settings
layout.width.dialog.md560pxStandard dialogs
layout.width.page1440pxMax container for marketing and reading layouts
layout.width.appnoneData-dense application views, full width

10.4Composing a SaaS dashboard

Most SaaS products are not pages on a grid. They are an app shell (persistent navigation and chrome) around a content region that has its own grid. Defining the shell's regions as part of the system removes a whole category of per-team layout decisions.

Dashboard composition rules

  1. Most important information top-left

    For left-to-right languages, readers scan from the top-left. Put the KPI or chart that answers "is everything OK?" first.

  2. Equal-height rows

    Cards in the same row share a height, so the grid stays visible and the eye can compare them.

  3. Spans from a short list

    Allow 3, 4, 6, 8, 9 and 12 columns on desktop. Avoid 5 and 7, which create misaligned edges.

  4. Mirror for right-to-left

    Use logical properties (inline-start, not left) so Arabic and Hebrew layouts mirror correctly from the same tokens.

10.5Desktop, mobile and alignment

Desktop and mobile are different layouts, not one layout scaled

On mobile, side navigation becomes a bottom bar or a drawer; multi-pane views become single screens with back navigation; tables become lists or cards. Decide these transformations once, as patterns, and every product inherits them.

Align to columns at the page level, to spacing inside components

Page regions and cards align to grid columns. Inside a card, elements align to each other using spacing tokens; a button doesn't need to snap to a column. Trying to grid everything produces rigid, awkward components.

Reflow, and its exceptions

WCAG 2.2 SC 1.4.10 requires content to reflow at a width of 320 CSS px without two-dimensional scrolling, except for content that requires a two-dimensional layout, such as data tables, maps and diagrams.[[c:wcag-reflow]] [[std]] Plan the 320px layout of every pattern; scroll horizontally only inside a table, never the whole page.

10.6Layout for complex enterprise applications

Enterprise applications push past the single-grid model. The layout system needs a vocabulary for structures that page grids don't describe:

Multi-pane layouts

List–detail and supporting-pane layouts that show two or three panes side by side on large screens and collapse to one on small. Material documents these as canonical layouts.[[c:m3-layout]]

Resizable and collapsible panes

Users of complex tools expect to resize panels. Define minimum and maximum widths as tokens, and remember user preferences.

Nested grids and container queries

A component placed in a narrow pane should adapt to its container, not the viewport. CSS container queries make components responsive to the space they're given.

Sticky regions and dense tables

Sticky headers, frozen first columns and horizontal scrolling inside tables keep context while users work through large datasets.

Layout tokens

"breakpoint": { "medium": "600px", "expanded": "840px", "large": "1200px", "xlarge": "1600px" },
"grid":       { "columns": { "compact": 4, "medium": 8, "expanded": 12 },
                "gutter": "{space.4}", "margin": { "compact": "{space.4}", "expanded": "{space.6}" } },
"layout":     { "sidebar": { "width": "240px", "collapsed": "64px" }, "topbar": { "height": "48px" },
                "width": { "prose": "68ch", "form": "560px", "page": "1440px" } }

A note on breakpoints as tokens: CSS custom properties can't be used inside media query conditions, so breakpoint tokens are compiled to constants (Sass variables, JS constants, or @custom-media where supported) rather than to var().

Grid and layout checklist

  • 4–5 named breakpoints, tokenised for design and code
  • Columns per breakpoint (e.g. 4 / 8 / 12)
  • Gutters and margins from the spacing scale
  • Hybrid container: fluid with a max width for reading
  • Content-width tokens for prose, forms and dialogs
  • App shell regions defined and sized by tokens
  • Mobile transformations defined as patterns
  • Every pattern works at 320px (tables excepted)
  • Logical properties for right-to-left support
  • Container queries for components in panes
