Chapter 21

Components as code

Chapter 15 introduced how components are built and shipped. This chapter goes deeper: what a well-built component looks like line by line, how to style it, how to make it accessible in code, which technology to choose, and how design and engineering stay aligned once the code exists.

Read this if

You're an engineer building system components, a design lead who wants to review them with confidence, or a decision-maker choosing technologies for the system.

What you'll leave with
  1. A complete, annotated example of a well-built component.
  2. A comparison of styling approaches and technology choices.
  3. A shared definition of done and a review checklist for design and engineering.

21.1A well-built component, line by line

Here's Ledgerly's button in React with TypeScript, two of the most common technologies for web design systems. If you don't write code, read the grey comments; they explain what each part is doing and why it matters. Everything in this chapter applies, with different syntax, to other frameworks.

// 1. The props, written down as a contract. TypeScript checks every use of the
//    button against this list, so a typo like variant="primery" is caught instantly.
type ButtonProps = {
  variant?: "primary" | "secondary" | "danger";   // one choice, not three switches
  size?: "sm" | "md" | "lg";
  icon?: IconName;                                  // a named icon from the system, not any image
  loading?: boolean;
} & React.ButtonHTMLAttributes<HTMLButtonElement>; // plus every normal button attribute

// 2. forwardRef lets screens reach the real button element, for focus management.
export const Button = React.forwardRef<HTMLButtonElement, ButtonProps>(function Button(
  // 3. safe defaults: secondary, medium, not loading
  { variant = "secondary", size = "md", icon, loading = false, disabled, children, ...rest },
  ref
) {
  return (
    <button                                    // 4. a real <button>: keyboard support is free
      ref={ref}
      type="button"                              // 5. never submits a form by accident
      className="button"
      data-variant={variant}                     // 6. styles read these; no colours in this file
      data-size={size}
      disabled={disabled || loading}             // 7. no double clicks while saving
      aria-busy={loading || undefined}           // 8. screen readers hear that it's working
      {...rest}                                  // 9. pass through ids, tests, aria-labels…
    >
      {loading ? <Spinner size="sm" /> : icon && <Icon name={icon} aria-hidden />}
      <span className="button__label">{children}</span>
    </button>
  );
});

A few of these lines deserve a little more explanation, because they're exactly the details that separate a system component from one built quickly for a single screen.

Using a real <button> element (comment 4) is the single most important accessibility decision in the file. Native buttons can be reached with the Tab key, pressed with Enter and Space, and are announced as "button" by screen readers, all without any extra code. Teams that build buttons out of plain boxes have to recreate all of that by hand, and usually miss something.

No colours or sizes in the file (comment 6). The component only says which variant and size it is; the stylesheet decides what that looks like, using tokens. That's why a rebrand never needs to touch this file.

Passing through everything else (comment 9) means teams can add a test ID or an accessible label without asking the system team for a new prop. The system stays small, and teams aren't blocked.

21.2Ways to style components

There are several ways to attach styles to components in code, and teams debate them passionately. The good news is that if your tokens are CSS variables, every approach can use them, so the choice matters less than it seems.

ApproachHow it works, simplyGood forWatch out for
Plain CSS with CSS variablesA normal stylesheet per component, using token variablesSimple, fast, works with any frameworkNeeds naming discipline to avoid clashes
CSS modulesLike plain CSS, but class names are made unique automaticallyNo clashes between components; easy to readRequires a build step
CSS-in-JSStyles written in JavaScript next to the componentStyles that depend on props; everything in one fileCan affect performance and server rendering; less popular than a few years ago
Utility classesMany tiny ready-made classes combined in the markupVery fast for product teams; tokens map to classesMarkup gets long; harder to enforce component-level rules

[[prac]] Our usual recommendation

For the system's own components: plain CSS or CSS modules, reading token variables, with variants selected by data attributes as in 21.1. It's fast, framework-independent and easy for anyone to read. Product teams can then use whatever approach they like for their own screens, as long as it reads the same token variables.

Whichever approach you choose, two rules hold. Styles only ever use tokens (Chapter 20). And styles should use logical properties, such as padding-inline rather than padding-left and padding-right, so layouts mirror correctly for right-to-left languages like Arabic and Hebrew without extra work.[[c:mdn-logical]]

21.3Accessibility, in code

Chapter 14 covered accessibility from the design side. In code, it comes down to a few habits that, once learned, become second nature.

Use the right element first

HTML already includes accessible elements for most jobs: buttons, links, form fields, labels, lists, headings, tables. They come with keyboard support and screen-reader meaning built in. Reach for extra accessibility attributes (ARIA) only when no native element fits. A common saying among accessibility specialists is that no ARIA is better than bad ARIA, because incorrect attributes can make things worse than none at all.

Follow the established patterns for complex components

For composites like menus, tabs, comboboxes and dialogs, the W3C's ARIA Authoring Practices Guide describes exactly how each should behave: which keys do what, where focus goes, what gets announced.[[c:aria-apg]] Following it means your components behave the way assistive-technology users already expect. Here's what that means for a dialog:

RequirementWhat the code must do
Announce itselfIdentify itself as a dialog and use its title as its name
Move focus inWhen it opens, move keyboard focus into the dialog (usually to the first field or the close button)
Keep focus insideTab and Shift+Tab cycle within the dialog, never into the page behind it
Close on EscapeThe Escape key closes it, unless closing would lose unsaved work
Return focusWhen it closes, focus goes back to the button that opened it
Hide the backgroundThe page behind is hidden from screen readers while the dialog is open

Six requirements, every one of which a quickly built dialog tends to miss, and all of which the system's dialog solves once for every product. That's the strongest argument for building complex components centrally.

21.4Choosing the technology

A design system's components have to be built in the same technology as the products that use them. That makes technology choice one of the biggest cost decisions in the whole system (Chapter 04).

Your situationCommon approachTrade-off
All web products use one frameworkBuild components in that frameworkSimplest and best developer experience. Tied to that framework.
Web products use several frameworksWeb Components (a browser standard) or a framework-neutral core with thin wrappersOne implementation works everywhere, but integration with each framework needs care.[[c:mdn-web-components]]
Web plus iOS and Android appsShared tokens; separate native components per platformNative feel and performance, but each component is built two or three times.
Legacy products that can't adopt new componentsShip tokens (CSS variables) and styles onlyVisual consistency without rewriting, but no shared behaviour.

Whatever you choose, notice the pattern: tokens are the part that works everywhere. Components may need to be built once per technology, but tokens are generated for every platform from one source. That's why tokens come first (Rule #4), and why they're the backbone when a company has a mix of old and new technology.

21.5Keeping design and engineering aligned

Most design–engineering friction in design systems comes from one question: when is a component actually done? If designers think "done" means the Figma file is published and engineers think it means the code is merged, nothing is ever really finished. Agree one definition, for both twins.

Definition of done (both twins)

  • Figma component and code component have the same name, props and values
  • Every variant and state exists in both, and in the workshop
  • Styles use tokens only; lint passes
  • Keyboard and screen-reader behaviour tested by a person
  • Visual, behaviour and automated accessibility tests pass
  • Documentation page complete (Chapter 16 template)
  • Release note written; Figma library and code package released together

Review questions for system pull requests

  • Does this change any prop, default or visual size? Then which version number changes?
  • Which components and products depend on what's changing?
  • Do the workshop pictures show only the intended changes?
  • Is Figma updated in the same release?
  • Is any new token or prop genuinely needed by two or more teams?
  • Has someone from design reviewed the result in the workshop?

The workshop (Chapter 15) is the meeting point. Designers review the real coded component there, in every state, rather than reviewing screenshots. Many teams also link each Figma component to its code and documentation, so it's one click from design to implementation and back. The tooling varies; the habit of reviewing the real thing together is what matters.

21.6Quality beneath the surface

System components are used everywhere, so their quality affects every product's speed and stability. A few engineering concerns deserve attention even though users never see them directly.

ConcernWhy it mattersGood practice
Package sizeEvery product downloads the components it uses; heavy components slow every product.Let products import only what they use; watch size on every release.
DependenciesEach outside library a component relies on adds size, risk and upgrade work.Keep outside dependencies few and well chosen; prefer browser features.
Server renderingMany products render pages on the server for speed; components must work there too.Test components in server-rendered pages before release.
Performance with real dataA list that's fine with 20 items may freeze with 10,000.Test level 4 components with realistic data volumes (Chapter 17).
Backwards compatibilityTeams update at different speeds.Follow the versioning rules; support the previous major version for a stated time.

The short version

What to remember from this chapter

  1. Good components use native elements, safe defaults, typed props, tokens only, and pass through standard attributes.
  2. Any styling approach works if it reads token variables; use logical properties for right-to-left support.
  3. Follow the established accessibility patterns for complex components, and test with a keyboard and a screen reader.
  4. Agree one definition of done for both twins, and review the real coded component together.
