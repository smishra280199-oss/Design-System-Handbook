Chapter 15

Building components in code

This chapter is for engineers, but it's written so that designers, product managers and founders can follow it too. Understanding how components are built in code is the best way to understand why design systems succeed or struggle.

Read this if

You build components, work closely with people who do, or keep running into "the design and the code don't match".

What you'll leave with
  1. What engineers mean by a component's "API" and "props", in plain words.
  2. How to keep design and code in step, and avoid three versions of everything.
  3. How components are tested and shipped so teams can trust them.

15.1What engineers mean by a component

New wordPropsThe settings you pass to a component in code, like the buttons on a TV remote: "variant", "size", "disabled".

Think of a TV remote. You don't need to know how the TV works inside. You just press buttons: volume up, channel 5, mute. A code component works the same way. Engineers use it by passing it a few settings, which they call props, and the component takes care of everything else: colours, spacing, keyboard behaviour, accessibility.

Here's what using the Ledgerly button looks like in code. Even if you've never written code, you can probably read it:

// Using the button: three settings and a label
<Button variant="primary" size="md" icon="send">
  Send invoice
</Button>

// The same button, disabled while saving
<Button variant="primary" loading>Saving…</Button>
New wordAPIThe list of settings a component accepts and what each one does. It's the "contract" between the component and the people using it.

The full list of settings a component accepts is called its API. A good component API is like a good remote: a few clearly labelled buttons that do exactly what they say, and nothing surprising. A bad one has sixty tiny buttons, half of which interfere with each other.

Once a component is in use, its API becomes a promise. If you rename variant to kind, every screen that uses the old name stops working. That's why changes to a component's API are treated as "breaking changes" (Chapter 05) and handled with care.

15.2Keeping design and code in step

In Chapter 12 we described components as twins: one in the design tool, one in code. Keeping the twins identical is one of the hardest ongoing jobs in a design system, and when it slips, things get messy fast.

ScenarioThree dropdowns, all called "Dropdown"
The situation

A mid-sized SaaS company has three engineering teams. Over two years, each built its own dropdown: one wraps an old open-source library, one is custom, and one was copied from the system and then modified.

What goes wrong

A keyboard accessibility bug is reported. It exists in all three, fixed differently in each. A design update to the dropdown takes three separate projects. New engineers don't know which one to use.

The way out

One dropdown in the system, matching the Figma version exactly; a migration guide; an automatic warning when the old ones are used; and a date after which the old ones are deleted.

One vocabulary, two places

The simplest and most effective rule: the names and options in Figma match the names and options in code, exactly. If the design file calls it "variant: primary / secondary / danger", the code does too. Not "kind", not "solid / outline", not "primary / default / destructive".

A shared workshop for components

Most system teams use a "workshop" tool where every component can be seen and tried in isolation, in every variant and state, outside of any product. Storybook is the most widely used one.[[c:storybook]] It gives designers, engineers and product managers one place to look at the real coded component, which makes it much easier to spot when the twins have drifted apart. Many teams also link each Figma component directly to its code and documentation, so a designer can jump from one to the other.

[[prac]] A monthly "twin check"

Once a month, a system designer and a system engineer spend an hour going through recently changed components side by side: Figma on one screen, the coded version on the other. List every difference and decide which twin is right. It's tedious, and it's the cheapest way we know to stop drift.

15.3Settings or building blocks?

There are two broad ways to make a component flexible, and choosing between them is one of the most important decisions in building a component library.

The first is configuration: one component with lots of settings. "Card with showImage, showAvatar, showFooter, footerAlign…" It's easy to start with, but every new need adds another setting, and eventually you get the forty-setting monster from Chapter 12.

The second is composition: several small, simple pieces that fit together, like Lego. You combine them to build exactly what you need. This is the code version of the "slots" idea from Chapter 12.

// Configuration: one component, many settings
<Card
  title="Revenue"
  showMenu
  image={chart}
  footerText="Updated 4 min ago"
  footerAlign="right"
  primaryAction="View report"
  // …and the next team will need one more
/>
// Composition: small pieces that fit together
<Card>
  <Card.Header title="Revenue">
    <Menu … />
  </Card.Header>
  <Card.Media>{chart}</Card.Media>
  <Card.Footer>
    Updated 4 min ago
    <Button>View report</Button>
  </Card.Footer>
</Card>

Neither approach is always right. Our rule of thumb is the same one we gave for design in Chapter 12. Small, frequently used components (button, checkbox, badge) should use a few clear settings, because consistency matters most and the options are limited. Bigger, container-like components (card, dialog, table, page layout) should use composition, because the content varies endlessly and settings can't keep up. [[prac]]

15.4No hard-coded values, ever

Chapter 11 showed the button's code using only named values, with no colour codes and no pixel numbers. That's the rule for every component in the system, and it's worth enforcing automatically, because it's very easy to slip.

Imagine an engineer is fixing a small layout issue at the end of a long day. The quickest fix is to type margin-top: 13px. It works, it ships, and nobody notices. But that one value doesn't change in compact mode, doesn't follow the spacing scale, and will be wrong after the next spacing update. Multiply that by a hundred small fixes and the system's foundations are quietly bypassed.

New wordLinterA tool that automatically checks code for problems and breaks of agreed rules, and flags them before the code is merged.

The fix is a linter rule: an automatic check that flags any raw colour code, pixel value or font size in component code, and suggests the named value to use instead. It runs every time someone submits code, so nobody has to remember. The same check can run in product teams' code too, which is one of the best ways to measure how much of the product really uses the system (Chapter 03).

15.5How you know a component works

When a component is used in 400 places, a bug isn't one bug: it's 400 bugs. That's why system components are tested more thoroughly than ordinary product code. Teams usually combine four kinds of testing:

Kind of testWhat it catchesHow it works, simply
Visual testsUnintended changes to how a component looksA tool takes a picture of every variant and state and compares it with the last approved picture. Any difference is flagged for a human to check.
Automated accessibility checksMissing labels, low contrast, incorrect rolesA tool scans each component for common accessibility rule breaks. It catches a lot, but not everything.
Behaviour testsThings that don't work, like a menu that won't open with the keyboardCode that pretends to be a user: clicks, types, presses keys, and checks the right thing happens.
Manual checksWhat automation can't judgeA person tries the component with a keyboard only and with a screen reader, especially for complex components.

Visual tests deserve special mention, because they catch exactly the kind of problem from the scenario in Chapter 05, where a small padding change broke layouts. If the system team had seen pictures of every button changing size, they'd have known it was a breaking change before shipping it.

A mistake we see often

"The automated checks passed, so it's accessible"

Automated accessibility tools are excellent at catching certain problems, like missing labels and poor contrast. They can't tell whether a keyboard user can actually complete a task, or whether a screen reader announcement makes sense. Always pair them with a real keyboard and screen-reader check for interactive components.

15.6Packaging and shipping components

Finished components are bundled into a package, which is how they reach product teams. Product teams install the package, a bit like installing an app, and can update it when a new version comes out. Chapter 05 covered version numbers and breaking changes; here's what that means day to day for the people building components.

  1. Every change gets a note

    Each change includes a one-line entry for the release notes, written for the people using the system: what changed and what, if anything, they need to do.

  2. Releases happen on a rhythm

    For example, new features every two weeks and urgent fixes whenever needed. Predictable releases let product teams plan their updates.

  3. Breaking changes are rare, grouped and announced

    Collect them into one bigger release, a few times a year, with a migration guide and, where possible, a script that makes the changes automatically.

  4. Old versions get a notice period

    Product teams can't always update immediately. Say how long old versions will receive important fixes, and stick to it.

What if teams use different technologies?

Large companies often have products built with different frameworks: one team on React, another on Angular, the mobile apps in Swift and Kotlin. Named values (tokens) work everywhere, because they're generated for each platform. Components are harder, because each technology needs its own version. This is one of the biggest cost drivers in Chapter 04, and a strong reason to agree on as few front-end technologies as possible.

The short version

What to remember from this chapter

  1. A component's settings (its API) are a promise. Keep them few, clear and stable.
  2. Use exactly the same names and options in Figma and in code, and check them regularly.
  3. Small components use a few settings; big ones are built from composable pieces.
  4. Ban hard-coded values with automatic checks, test visually and for accessibility, and ship on a predictable rhythm.
