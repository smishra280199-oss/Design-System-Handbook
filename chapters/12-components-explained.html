Chapter 12

Components, explained

Buttons, text fields, menus, tables: components are what most people picture when they hear "design system". This chapter takes one apart, piece by piece, so you understand what you're actually building before you build a single one.

Read this if

You're new to components, you're about to plan a component library, or you've heard words like "variant", "prop" and "slot" and want them explained simply.

What you'll leave with
  1. What a component really is, in design and in code.
  2. The vocabulary: parts, options, states and slots.
  3. A realistic sense of how many components a product needs.

12.1What a component is

Think about the light switches in your home. You don't design a new switch for every room. You pick one model, and every room gets the same one. It works the same way everywhere, you know exactly what it does, and if a better model comes out, you can swap them all.

A component is the same idea for software: a piece of interface that's designed once, built once and used everywhere. A button. A text field. A dropdown menu. A date picker. A table.

The important part, and the part people often miss, is that a design system component exists twice, as a pair of twins. One twin lives in the design tool, where designers drag it into their screens. The other lives in code, where engineers use it to build the real product. The two twins have the same name, the same options and the same behaviour. When the twins match, a designer's screen and the shipped product match too.

The design twin

In Figma (or similar)

A "master" that designers place into screens. Change the master and every copy in every design file can update.

The code twin

In the code package

A piece of code engineers use with one line, like <Button variant="primary">Save</Button>. Improve it and every screen gets the improvement on the next update.

ScenarioWhen the twins don't match
The situation

The Figma button has four types: primary, secondary, tertiary and danger. The code button has three, and calls them "solid", "outline" and "ghost".

What goes wrong

A designer uses "tertiary" in a design. The engineer guesses it means "ghost". It doesn't quite match. Design review flags it. Everyone loses half a day.

The fix

One list of names and options, agreed once and used in both places. Chapter 15 covers how to keep the twins in step.

12.2Anatomy: the parts of a component

Even a simple component is made of several parts, and naming them makes design discussions much faster. "The helper text is too close to the field" is a lot clearer than "that grey bit underneath is a bit squashed". Here's an ordinary text field, taken apart.

12.3Options: types, sizes and settings

New wordVariantAn approved version of a component, like a primary or a secondary button. Same component, different look for a different purpose.

A single component usually comes in a few approved versions. A button might come in a primary version for the main action on a screen, a secondary version for less important actions, and a danger version for things like "Delete account". It might also come in three sizes. Designers call these variants; engineers often call the settings that control them props (short for "properties"). They're the same idea: the switches and dials on a component.

Options are powerful, but they're also where components go wrong. Every option you add is something to design, build, test, document and maintain, for every combination. Three types and three sizes is nine combinations. Add "with icon" and "loading" and it's thirty-six. That's why mature systems are careful about adding options. A good question to ask before adding one: is this a real, repeated need in more than one team, or a one-off for a single screen?

A mistake we see often

The button with forty settings

Every team asks for one small option: a different colour, a different corner, a special icon position. Each request is reasonable, and the system team says yes each time. Two years later the button has forty settings, nobody understands them all, and it's slower to use the system button than to build your own. Saying "no" (or "build that locally") is part of looking after a component.

12.4States: one component, many situations

A component doesn't just sit there looking nice. People hover over it, click it, tab to it with the keyboard, type into it, make mistakes in it. Each of these situations is called a state, and each one needs to be designed. Here's a text field in eight of them.

When a component looks broken in production, it's very often because a state was never designed. Nobody thought about what happens when the text is too long, or when the data is still loading, or when there's an error and the field is also disabled. Designing every state up front is one of the biggest quality gains a design system gives you. Chapter 14 includes a full checklist.

12.5Small parts and big parts

Some components are small and simple: a button, a checkbox, a badge. Others are made from several smaller ones: a search bar is a text field, an icon and a button; a data table is made of headers, cells, checkboxes and pagination. Brad Frost's Atomic Design popularised this idea of building big things from small things, a bit like atoms making molecules.[[c:frost-atomic]]

New wordSlotAn empty space inside a component where you can put other content, like a picture frame you fill yourself.

For bigger components, there's an important design choice. Do you give the component lots of settings to cover every case, or do you give it slots, empty spaces where teams can put their own content? A card is a good example. Instead of building "card with image", "card with avatar", "card with chart" and so on, you build one card with a few slots and let teams fill them.

Slots aren't always the answer. A button shouldn't have a slot for "anything you like", because then someone puts a dropdown inside it. As a rough rule: small, frequently used components should be strict, with a few clear options; larger, container-like components should be flexible, with slots. Alla Kholmatova's book Design Systems describes this as a balance between strict and loose systems, and points out that more modular isn't automatically better.[[c:kholmatova]]

Systems grow over time, of course. At IBM, Layer One's founder worked on systems with 71 components for an airline and more than 40 for a pharmacy storefront.[[c:layerone]] But even those started with the everyday basics. The order you build them in matters a lot, and that's the subject of the next chapter.

The short version

What to remember from this chapter

  1. A component is designed once, built once and used everywhere, and it exists as twins in design and code with identical names and options.
  2. Name a component's parts (its anatomy) so everyone can talk about it precisely.
  3. Options multiply effort; add them only for real, repeated needs.
  4. Design every state, not just the default. Use slots for big, container-like components.
