Chapter 18

Component architecture

Architecture sounds intimidating, but the idea is simple: decide which parts of your library are built from which, and keep those relationships tidy. Get it right and the library is easy to change for years. Get it wrong and every small change breaks something unexpected.

Read this if

You're setting up a component library, your library has become hard to change, or you want to understand how mature systems are organised under the surface.

What you'll leave with
  1. A layered model for organising components, and the rules that keep it healthy.
  2. The main ways components are put together, explained with simple examples.
  3. How to organise the files and packages, and how to manage dependencies as the library grows.

18.1What "architecture" means for components

Think about the wiring in a building. You don't see it, but it decides a lot: whether you can add a new socket easily, whether a fault in the kitchen trips the whole house, whether an electrician can understand it ten years later. Good wiring is organised in circuits, each with a clear job, all running back to one board.

Component architecture is the wiring of your design system. It answers three questions. What is each component built from? (A dialog uses buttons, which use text styles, which use tokens.) Which way do dependencies run? (A button can use an icon, but an icon should never need a button.) And where does each kind of logic live? (Is keyboard behaviour inside the dialog, or in a shared piece that menus use too?)

ScenarioThe text change that broke forty components
The situation

An engineer adjusts the line spacing of the library's internal Text component to fix a problem in one tooltip.

What goes wrong

Forty other components use the same Text component. Buttons grow by 2 pixels, table rows shift, and three product teams report layout bugs after the next update.

What architecture changes

A clear map of which components depend on which would have shown the "blast radius" before the change. The fix belonged in the tooltip, not in a shared building block.

18.2Layers, and the one rule that keeps them healthy

Most well-run component libraries are organised in layers, a little like the layers of a design system in Chapter 01, but zoomed in on the components themselves. Each layer is built only from the layers beneath it.

New wordPrimitiveA low-level building block, often invisible, that other components are made from: a box with spacing, a piece of styled text, a stack that spaces its children evenly.

The layer most people haven't heard of is primitives. These are tiny, mostly invisible building blocks: a Box that applies spacing and colour tokens, a Stack that lines things up with even gaps, a Text that applies a text style. Primitives mean that base components don't each reinvent "how do I apply spacing tokens". They're also handy for product teams building local components, because using primitives keeps local work on-system.

The one rule that keeps layers healthy is: dependencies only point down. A dialog may use a button. A button must never use a dialog. A primitive must never know that tables exist. When this rule is broken, you get circular dependencies (two components each needing the other), and changes start causing surprises far away from where they were made.

18.3Separating how it works from how it looks

Every interactive component has two quite different jobs. One is behaviour: what happens when you click, which element has keyboard focus, what a screen reader announces, when a menu opens and closes. The other is appearance: colours, spacing, corner rounding, text styles. Mature libraries increasingly keep these two jobs apart.

This is why headless libraries (Chapter 13) have become so popular. They provide the behaviour layer, which is the genuinely difficult part, already tested against the expected keyboard and screen-reader patterns.[[c:aria-apg]] Your team supplies the appearance layer using your own tokens. The result looks entirely like your brand but behaves like a well-tested standard component.

Even if you build everything yourself, the separation is worth keeping. Put behaviour into shared pieces of logic that several components can use. A "dismiss on Escape and return focus" behaviour, for example, is needed by dialogs, side panels, menus and popovers. Write it once, test it once, and use it in all four.

18.4Four ways to put components together

When you look inside mature component libraries, you see the same few construction techniques again and again. Here they are in plain language, with a tiny code example of each for the engineers. You don't need to read the code to follow the idea.

1. Compound components: a family that works together

Some components are really a small family of parts that only make sense together. Tabs are the classic example: a list of tabs, the tabs themselves, and a panel for each tab. Instead of one giant component with dozens of settings, you provide each part separately and let them coordinate behind the scenes. It reads almost like a sentence.

<Tabs defaultValue="invoices">
  <Tabs.List>
    <Tabs.Tab value="invoices">Invoices</Tabs.Tab>
    <Tabs.Tab value="payments">Payments</Tabs.Tab>
  </Tabs.List>
  <Tabs.Panel value="invoices">…</Tabs.Panel>
  <Tabs.Panel value="payments">…</Tabs.Panel>
</Tabs>

The parts share information quietly (which tab is selected, which panel to show, where keyboard focus goes), so the person using them doesn't have to wire it up. Use this for any component made of a fixed family of parts: tabs, menus, accordions, selects.

2. Slots: spaces for any content

We met slots in Chapter 12. In code, a slot is usually just "put whatever you like here", with the component controlling the frame around it. A card with header, media, body and footer slots is the typical example. Use slots for containers whose content varies endlessly: cards, dialogs, side panels, page layouts.

3. Changing what something renders as

Sometimes you want something that looks like a button but is really a link to another page, because it navigates rather than performs an action. That distinction matters for accessibility: screen readers announce links and buttons differently, and people expect different keyboard behaviour. Many libraries let a component render as a different underlying element while keeping its appearance.

// Looks like a button, behaves like a link (because it navigates)
<Button as="a" href="/invoices/new" variant="primary">New invoice</Button>

Use this sparingly and document it clearly. "Actions use buttons, navigation uses links" is a rule worth keeping, even when they look alike.

4. Controlled and uncontrolled

Some components hold a piece of information that can change: whether a dialog is open, which tab is selected, what's typed in a field. The question is who keeps track of it. In an uncontrolled component, the component keeps track itself; you just give it a starting value. In a controlled component, the product screen keeps track and tells the component what to show. React's documentation explains the idea well.[[c:react-controlled]]

// Uncontrolled: "start on invoices, then look after yourself"
<Tabs defaultValue="invoices">…</Tabs>

// Controlled: "I'll tell you which tab is selected, and you tell me when it changes"
<Tabs value={tab} onValueChange={setTab}>…</Tabs>

Good libraries support both. Uncontrolled is simpler for everyday use. Controlled is needed when the screen must react to changes, for example to save the selected tab in the web address so people can share a link to it.

18.6Dependencies, ownership and change

As a library grows, the relationships between components become as important as the components themselves. Nathan Curtis's series on releasing design systems devotes a whole article to this: how a change to one component travels up to everything that depends on it.[[c:curtis-releasing]] Three habits make that manageable.

Keep a dependency map. Know which components use which. Many tools can generate this automatically from the code. Before changing a shared piece, look at what depends on it. In our scenario, that would have shown forty components relying on Text.

Name an owner for every component. In larger organisations, each component (or group of components) has a named owner who reviews changes to it. Code platforms let you record this in a simple file, so the right person is asked automatically whenever someone proposes a change.

Change the right layer. When fixing a problem, fix it at the lowest layer where it genuinely belongs, and no lower. If only the tooltip needs tighter lines, change the tooltip. If every component needs tighter lines, change the text token. The mistake in our scenario was fixing a local problem in a shared layer.

[[prac]] Architecture review, quarterly

Once a quarter, look at the dependency map with fresh eyes. Are there arrows pointing upwards? Components nobody uses? Shared pieces with an enormous blast radius? An hour of review prevents the slow tangle that eventually makes teams say "we need to rebuild the design system".

The short version

What to remember from this chapter

  1. Organise the library in layers (tokens, primitives, base, composite, recipes) where dependencies only point down.
  2. Keep behaviour separate from appearance, so rebrands and accessibility fixes don't collide.
  3. Use compound components for families of parts, slots for containers, and support both controlled and uncontrolled use.
  4. Give every component the same file structure, a named owner and a place on a dependency map.
