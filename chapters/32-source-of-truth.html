Chapter 32

The single source of truth

If people have to search Figma, a wiki, Storybook, three Slack channels and someone's memory to answer one question, they'll stop asking and start guessing. A design system needs one home: an internal portal where everything about the system lives. This chapter shows what to put in it and how to keep it trustworthy.

Read this if

Information about your system is scattered, your docs are out of date, or you're about to build or redesign your documentation site.

What you'll leave with
  1. Everything a design system portal should contain, and why.
  2. An information architecture and page templates you can adapt.
  3. How to keep the portal accurate, findable and owned.

32.1Why one home matters

ScenarioSeven places to check, zero answers
The situation

An engineer wants to know whether the old modal is being retired. The answer might be in the wiki, the Figma file, Storybook, the release notes, a Slack thread or the roadmap spreadsheet.

What goes wrong

The wiki says one thing, a three-month-old Slack thread says another, and the roadmap spreadsheet hasn't been updated. The engineer asks in the channel, waits a day, and builds with the old modal anyway.

What one home changes

The modal's documentation page shows "Deprecated: removed in 6.0 (March). Use Dialog. Migration guide →". One place, one answer, always current.

A single source of truth doesn't mean everything is stored in one tool. Figma files will stay in Figma and code in the repository. It means there's one front door that everyone knows, which links to everything else and says what's current. If it's in the portal, it's true. If it isn't in the portal, it isn't official.

32.3Information architecture

The structure of the portal should match how people think about their work, not how the system team is organised. People arrive with a task: "I need a dropdown", "how do I theme this?", "is this changing?" The navigation should lead them straight to the answer.

Two structural choices make a big difference. First, entry points by role: a designer and an engineer need different first steps, so "Get started" offers a path for each. Second, the Updates section is always one click away, because "what's changed?" is one of the most common questions, and burying it means people miss breaking changes.

32.4The pages that matter most

A few pages do most of the work. Get these right first.

Home page

Answer "what's new and where do I go?"

Latest release and any upcoming breaking change, quick links by role, search front and centre, next office hours, and one short "start here" link.

Component page

Everything about one component

The nine-section template from Chapter 16: summary, when not to use, examples, anatomy, code and Figma, accessibility, writing, do's and don'ts, status and history.

Token pages

Values, purpose, and use

Each token with its value in every theme, a swatch or preview, what it's for, and an example in design and code. Generated from the token source, so it's never out of date.

Release notes

What changed, for users

Newest first, each release with breaking changes first, then new things, then fixes. Links to migration guides and the components affected.

Support page

How to get help

Office hours times (in several time zones), how to book, channels, response times, the FAQ and troubleshooting, and who owns what.

Contribute page

How to take part

The request form, contribution levels, what to expect at each step, and recent contributions to show it's real.

32.5Keeping it accurate

An out-of-date portal is worse than none, because people trust it and get it wrong. Accuracy has to be built into how the system works, not left to good intentions.

PracticeHow it helps
Generate what you canProps tables, token values, live examples and release notes come straight from the code and token source, so they can't drift.
Docs in the definition of doneA component change isn't finished until its page is updated (Chapter 21). Reviewers check it like code.
An owner for every sectionNamed in the page footer, so readers know who to ask and owners know what's theirs.
"Last reviewed" datesPages not reviewed in six months are flagged automatically for their owner.
Feedback on every page"Was this helpful?" and "report a problem" links send issues straight to the owner.
Versioned docsTeams on an older major version can still read the docs for their version.
Automatic checksBroken links and missing pages (a component with no docs) flagged in the build.

32.6Making it easy to find things

Most people arrive at the portal with a search, not a browse. Search quality is therefore the single biggest factor in whether people find answers.

  • Search everything: components, tokens, patterns, guides, release notes and FAQs, in one search box.
  • Teach search your synonyms: "modal" should find Dialog; "chip" and "pill" should find Tag. Use the keywords from Chapter 16.
  • Watch failed searches: searches that return nothing are a free list of missing content or missing synonyms.
  • Cross-link generously: every component links to the patterns that use it; every pattern links to its components; deprecated pages link to replacements.
  • Keep an FAQ and a troubleshooting page, built from the questions that actually recur in the channel and office hours.

32.7Building the portal

There are three common ways to build a portal, and the right one depends mostly on your size and how much engineering time you have.

The short version

What to remember from this chapter

  1. Give the system one front door. If it's in the portal it's true; if not, it isn't official.
  2. Include everything people need: foundations, tokens, components, patterns, guides, contributing, updates, support and ownership.
  3. Structure it around people's questions, with role-based entry points and updates always one click away.
  4. Keep it accurate by generating what you can, naming owners and dating reviews, and invest in search.
