Chapter 06

Understanding design foundations

Before buttons and menus, there's a smaller set of decisions that everything else inherits: colours, text, spacing and layout. They're the cheapest part of a design system to set up, and the most expensive part to get wrong.

Read this if

You're about to decide your product's colours, type or spacing, or you want to understand how a design decision turns into code without anyone retyping it.

What you'll leave with
  1. What counts as a "foundation", and what doesn't.
  2. Why changing a foundation is a big deal, explained through a simple idea called blast radius.
  3. How a decision travels from a designer's head into the product's code.

06.1What foundations are

Think of building a house. Before anyone chooses kitchen cabinets, someone has decided the ceiling height, the size of a standard door and where the plumbing runs. Every room inherits those decisions. Get them right and everything fits. Get them wrong and every room fights the house.

Foundations are the same thing for a digital product. They're the basic visual decisions that every button, card and page inherits. They aren't components themselves, but every component is built out of them. Different design systems give them slightly different names (IBM's Carbon calls them "elements"; Google's Material calls them "styles" and "foundations"), but the list is remarkably consistent.[[c:carbon-spacing,m3-color]]

06.2Why foundations matter: blast radius

Here's a useful way to think about any design decision: how many places does it affect? We call that its blast radius. Changing the label on one button affects one button. Changing the colour used for all secondary text affects every screen in every product. Foundations have the biggest blast radius of anything in a design system.

That double edge is the whole point. A wide blast radius is what makes foundations powerful: fix a contrast problem once and it's fixed everywhere. It's also what makes them risky: pick a text size that's slightly too small and every screen inherits it. Four things in particular are decided at this level:

QualityWhether text is readable and whether headings stand out from body text is decided here. Muddy text sizes make every screen muddy.
ConsistencyOffering twelve spacing values instead of "whatever looks right" makes consistency the default instead of something checked in review.
FlexibilityNaming colours by their job (07.4) is what later makes dark mode and new brands possible without touching any components.
SpeedFewer choices mean faster decisions. "Which of these twelve?" is a much quicker question than "how many pixels?"

06.3From a designer's decision to the product's code

Here's the problem foundations have to solve. A designer decides the primary button should be a particular shade of orange. In a traditional handover, she writes #AB2800 on a spec. An engineer copies it into the code. Another engineer, on another team, copies it from a screenshot and gets #AA2900. A year later, nobody knows which is right, and changing it means finding every copy.

Design tokens fix this by making sure a decision is written down once and everything else reads from that one place. The steps look like this:

Notice that there are two names in the middle. The first, brand-700, describes the colour itself: it's the 700 shade of our brand orange. The second, action-primary, describes its job: it's the colour for main actions. Buttons use the job name, not the colour name. That small extra step is what makes dark mode possible later. In dark mode, "the colour for main actions" can point to a lighter orange, and no button needs to change. Chapter 07 explains this properly.

A shared format for tokens

For years, every design tool and code library stored tokens in its own format, which made moving between them painful. In October 2025 the W3C Design Tokens Community Group, an industry group that includes people from Adobe, Google, Microsoft and others, published the first stable version of a shared format.[[c:dtcg-announce,dtcg-format]] [[doc]] It's a simple structured text file. Each token has a type (colour, size and so on) and a value, and tokens can point to each other using curly brackets, like {color.brand.700}. (Strictly speaking it's a community group report rather than an official W3C standard, but it's the format most token tools are now converging on.)

Here's what a small piece of Ledgerly's tokens looks like in that format. You don't need to be able to read code to get the idea: raw colours at the top, job names that point to them in the middle, and a button that points to a job name at the bottom.

[[prac]] Tokens first, components second

This is Rule #4 of how we work, and the most important sequencing decision in a design system. Components built before tokens exist end up with colour codes and sizes typed directly into them, which someone has to find and replace later. Tokens set up first make every component ready for themes and changes from day one.

The short version

What to remember from this chapter

  1. Foundations are the basic visual decisions everything else inherits: colour, type, spacing and layout, plus a few more.
  2. They have the biggest blast radius in the system, so they deserve the most careful thought.
  3. Tokens let a decision be written once and read everywhere: by design tools and by the code for every platform.
  4. Name the raw value, then name its job. Components use the job names.
