Chapter 06

Understanding design foundations

Foundations are the small set of decisions that every pixel in your product inherits. They are the cheapest part of a design system to build and the most expensive part to get wrong.

Read this if

You are about to define colour, type or spacing for a product, or you need to understand how a design decision becomes code without being re-typed by hand.

What you'll leave with
  1. A clear list of what counts as a foundation, and what doesn't.
  2. An understanding of "blast radius": why foundation changes are high-impact.
  3. The pipeline from a design decision to a token to production code, which the rest of Part 02 fills in.

06.1What foundations are

A foundation is a category of fundamental visual decision that is not itself a component but is used by every component. Public systems differ in naming (Carbon calls them "elements", Material calls them "styles" and "foundations"), but the categories are remarkably consistent.[[c:carbon-spacing,m3-color]]

06.2Why foundations matter: blast radius

Every decision in a design system has a blast radius: the number of places it affects. A component property affects one component. A foundation affects all of them. That is why foundations are both the highest-leverage and the highest-risk part of the system.

Foundational decisions shape four outcomes:

QualityContrast, legibility and hierarchy are decided here. A type scale with too-small steps produces muddy hierarchy in every screen.
ConsistencyA constrained set of values (say 12 spacing values instead of "whatever looks right") makes consistency the default rather than a review task.
ScalabilityA semantic layer (07.4) makes themes, dark mode and new brands possible without touching components.
Delivery speedFewer choices mean faster decisions. "Which of these 12 spacing values?" is a quicker question than "how many pixels?"

06.3From decision to token to code

The reason foundations can be changed safely is that they are never typed twice. A decision is captured once as a design token, a named value stored in a platform-agnostic format, and compiled into every platform's code by a build step.

A shared format

Until recently every tool used its own token format. In October 2025 the W3C Design Tokens Community Group published version 2025.10 of the Design Tokens Format Module, its first stable specification.[[c:dtcg-announce,dtcg-format]] [[doc]] It defines a JSON format where each token has a $value and a $type, groups nest with dot-path names, and tokens reference each other with curly braces ({color.brand.700}). Note that it is a Community Group report, not a formal W3C Standard; it is nevertheless the format most token tools now converge on. This is what the Ledgerly tokens look like in it:

Rule #4 of how we work, and the most important sequencing decision in a system. Components built before the token layer exists end up with hard-coded values that must be found and replaced later. Tokens built first make every component themeable from day one.
