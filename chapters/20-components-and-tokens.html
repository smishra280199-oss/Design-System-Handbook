Chapter 20

Components and tokens

Part 02 showed how tokens hold your foundation decisions. This chapter shows how components plug into them: which parts of a component become tokens, how to name them, when a component deserves its own tokens, and how to keep the connections healthy as everything changes.

Read this if

You're connecting components to tokens, planning theming or multiple brands, or your dark mode keeps breaking in specific components.

What you'll leave with
  1. A clear map from a component's parts to the tokens it uses.
  2. A naming pattern and a decision guide for component-level tokens.
  3. How tokens connect to Figma and code, and how to audit them over time.

20.1Where components meet tokens

A quick reminder of the three levels of tokens from Chapter 07. Primitive tokens are the raw paints and sizes (brand.700, space.4). Semantic tokens name a job (action.primary.bg, text.secondary). Component tokens name a specific use inside a specific component (button.primary.background). Each level points to the one below.

The question this chapter answers is: how should a component get its values? There are two sensible answers and one bad one.

Good

Component uses semantic tokens

The button's background is action.primary.bg. Simple and enough for most single-brand products.

Good

Component has its own tokens

The button's background is button.primary.background, which points to action.primary.bg. More flexible, more to maintain.

Bad

Component uses primitives or raw values

The button's background is brand.700 or #AB2800. Dark mode and theming break here first.

ScenarioDark mode works everywhere except the date picker
The situation

Ledgerly launches dark mode. Every screen looks right, except the date picker, whose selected day stays bright orange on a white square.

The cause

The date picker was built quickly and used brand.700 and neutral.50 directly. Those are paints, not jobs, so dark mode had no way of switching them.

The fix, and the lesson

Point the date picker at job names (action.primary.bg, bg.surface) and add an automatic check that flags any component using primitives. One component fixed, a whole class of bugs prevented.

20.2Which parts of a component become tokens

Start from the component's anatomy (Chapter 12). For each part, ask: which of its visual properties could ever need to change with a theme, a brand, a density or a platform? Those properties should come from tokens. Here's the map for Ledgerly's text field.

Two things are worth noticing. First, every property that responds to a theme, brand or density is a token. Properties that never change, like the fact that the label sits above the field, are just part of the component's design and don't need tokens. Second, this map is useful even if you decide not to create component tokens. It tells you exactly which semantic token each part should use, which is what prevents the date picker problem.

20.3Naming component tokens

Component tokens multiply quickly. Ten components with ten tokens each is already a hundred names. A consistent naming pattern is what keeps them guessable (Layer One's Rule #3). This pattern works well:

{component}.{variant}.{part}.{property}.{state}

button.primary.container.background             // default state can be left out
button.primary.container.background.hover
button.primary.label.color
input.container.border.error                // no variant needed
table.row.background.selected

Use the anatomy part names from the component's documentation, so the token name, the anatomy diagram and the Figma layer names all match. Leave out levels that don't apply rather than inventing filler like "default". And use the same property words everywhere: if one component says background, none should say bg or fill.

[[prac]] Test your names with a newcomer

Show a new designer or engineer the anatomy diagram of a component they haven't seen, and ask them to guess the token for, say, the border of the error state. If they get it right, or nearly right, your naming works. If they can't, simplify.

20.4When does a component deserve its own tokens?

Component tokens are powerful, but they have a real cost: more names to create, document and keep in step across Figma and code. Nathan Curtis has even cautioned that the industry may be "focused too much on design tokens" at the expense of other parts of a system.[[c:curtis-interview]] So don't create them by default. Create them when you have a reason.

SituationComponent tokens?Why
One brand, light and dark modeusually noSemantic tokens already switch with the theme.
Several brands that differ only in colourusually noA brand level under the semantic tokens handles it (Chapter 07).
Brands that style specific components differently (rounder buttons, flat cards)yesEach brand can override just those components' tokens.
White-label products where customers adjust specific componentsyesGives a safe, limited list of things customers can change.
A component that genuinely differs from the semantic ruleyes, for that partRecords the exception in one visible place instead of hiding it in code.
Native apps that need platform-specific sizesyes, for sizesiOS and Android can map component sizes to their own guidelines.

A good middle path, which many teams use, is to define component tokens only for the properties that actually vary. Ledgerly might give buttons a button.container.radius token, because one brand wants pill-shaped buttons, while letting the button's colours use semantic tokens directly. That keeps the token list short and purposeful.

20.5Tokens in Figma and in code

The connection between a component and its tokens has to exist on both sides of the twins.

In Figma

Figma's variables let designers store token values and attach them to the properties of a component's layers: a fill, a stroke, padding, corner radius.[[c:figma-variables]] Variables can have several modes, such as light and dark or brand A and brand B, so switching a mode restyles every component that uses them. When the variable names match the token names in code, designers and engineers are literally talking about the same thing.

In code

The token pipeline generates the same values for code, typically as CSS variables on the web. The component's styles then reference only those names. Here's how a second brand changes just the button's shape, without touching any component code:

/* tokens: component level, in the shared format */
{
  "button": {
    "container": {
      "radius": {
        "$type": "dimension",
        "$value": "{radius.control}"
      }
    },
    "primary": { "container": { "background": {
      "$type": "color",
      "$value": "{color.action.primary.bg}"
    } } }
  }
}
/* generated CSS */
:root {
  --button-container-radius: var(--radius-control);
  --button-primary-container-background:
    var(--color-action-primary-bg);
}
/* brand B overrides one component token */
[data-brand="b"] {
  --button-container-radius: 999px;
}

/* Button.css never changes */
.button { border-radius: var(--button-container-radius); }

That's the whole point of component tokens in one picture: brand B gets pill-shaped buttons by changing one value, and no component code is touched. The token format used here is the shared Design Tokens Community Group format from Chapter 06.[[c:dtcg-format]]

20.6Keeping tokens and components in sync

Tokens and components drift apart over time, just like Figma and code do. A component gets a quick fix with a raw value. A token is renamed but one component still uses the old name. A token is created for a feature that was later removed. A light quarterly audit catches most of this.

CheckWhat it findsHow
Raw values in componentsColours, sizes or spacing typed directly into component stylesAn automatic lint rule on every code change
Primitives used in componentsComponents pointing at paints instead of jobs (the date picker problem)A lint rule that only allows semantic and component tokens
Unused tokensTokens no component or product uses any moreA script comparing the token list with usage in code
Missing tokensProperties that change with themes but have no tokenSwitch every theme and density in the workshop and look for parts that don't change
Figma–code mismatchVariables in Figma that don't match tokens in codeCompare the exported variable list with the token source

Before changing any token, check its blast radius: which components and products use it? The same dependency map from Chapter 18 works here. A token used by one component is safe to change; a token used by forty is a release with notes and screenshots.

The short version

What to remember from this chapter

  1. Components should use semantic or component tokens, never primitives or raw values.
  2. Map each part of a component's anatomy to the token it uses; that map prevents theme bugs.
  3. Create component tokens only where something genuinely varies by brand, platform or customer.
  4. Connect tokens in Figma (variables) and code (CSS variables) with matching names, and audit them every quarter.
