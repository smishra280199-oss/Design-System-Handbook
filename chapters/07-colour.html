Chapter 07

Colour systems

Colour is the foundation teams get wrong most often, and the one where getting it right pays back fastest. This chapter goes from colour models to a production token architecture, and every value in it is computed, not guessed.

Read this if

You are defining or repairing a palette, adding dark mode or a second brand, or you keep finding contrast failures in audits.

What you'll leave with
  1. Why OKLCH is the right model for building a system palette, and where it still needs checking.
  2. A repeatable method for generating accessible colour ramps, with a complete worked palette.
  3. A three-tier token architecture that makes themes, dark mode and multiple brands a configuration change.

07.1Colour models: how colour is described

A colour model is a way of describing a colour with numbers. The model you build your palette in decides which questions are easy to answer. For a design system the most important question is "is this lighter or darker than that, and by how much?", because that is what contrast, hierarchy and state changes depend on.

ModelDescribes colour asGood forProblem for design systems
RGBAmounts of red, green and blue light (0–255)How screens work; final outputNot human-readable. Nobody can predict what rgb(204 60 0) looks like, or how to make it 10% lighter.
HEXRGB written in base 16 (#cc3c00)Compact; universal in tools and codeThe same as RGB, and even less readable.
HSLHue (angle), saturation, lightnessPicking colours by intuition"Lightness" is not perceived lightness: hsl(60 100% 50%) (yellow) and hsl(240 100% 50%) (blue) claim the same lightness but look nothing alike.
HSV / HSBHue, saturation, value (brightness)Colour pickers in design toolsSame flaw as HSL; "value 100%" is a different perceived brightness for every hue.
OKLCHLightness (0–1), chroma (colourfulness), hue (angle)Building palettes, ramps and themesSome combinations fall outside what screens can show (07.2), and lightness is close to, but not identical with, WCAG contrast.

Perceptual versus non-perceptual

RGB, HSL and HSV are non-perceptual: equal numeric steps do not look like equal steps to the human eye. A perceptual colour space is designed so that numeric distance tracks perceived difference. Oklab, published by Björn Ottosson in 2020, is a perceptual space designed for exactly this.[[c:ottosson-oklab]] OKLCH is the same space in polar form: lightness, chroma and hue. It is part of CSS Color Module Level 4 and supported natively in current browsers as oklch().[[c:css-color-4]] [[std]]

Lightness, chroma and hue

Lightness L 0 → 1

How light the colour looks. The axis that drives contrast, hierarchy and states. Black is 0, white is 1.

Chroma C 0 → ~0.37

How colourful it is. 0 is grey. Unlike HSL saturation, the maximum depends on hue and lightness.

Hue H 0° → 360°

Which colour family. Every swatch in this row has L 0.70, so they all look equally light.

Why OKLCH is particularly useful for design systems

  1. Predictable lightness

    Step 700 can mean "this lightness" in every hue. So state changes, hierarchy and contrast behave the same across your whole palette.

  2. Independent axes

    Change hue (a new brand) without changing lightness, and so without breaking contrast. In HSL, rotating hue silently changes perceived lightness.

  3. Generated, not hand-picked, ramps

    Ramps become a formula (a lightness curve plus a chroma envelope), so new hues, brands and white-label themes come out consistent.

  1. Better gradients and mixing

    Interpolating in OKLCH avoids the grey, muddy midpoints of sRGB blends (07.7).

  2. Wide-gamut ready

    OKLCH can describe the more vivid colours of Display P3 screens. In sRGB values you can't even write them down.

  3. Native in CSS and the token spec

    oklch() is in CSS Color 4, and the DTCG 2025.10 format can store OKLCH components directly.[[c:css-color-4,dtcg-format]] Tailwind CSS moved its default palette to OKLCH in v4.0.[[c:tailwind-v4]] [[doc]]

Two caveats that matter

1. Not every OKLCH colour can be displayed. Screens have a gamut, a range of colours they can physically produce. High chroma at very light or very dark lightness often falls outside sRGB. Tools must gamut-map (reduce chroma until the colour fits); our generator does this, and marks each chip where it happened.

2. OKLCH lightness is not WCAG contrast. WCAG 2 contrast is computed from relative luminance, a different formula.[[c:wcag-contrast]] Equal OKLCH lightness gives similar contrast across hues, not identical. You still validate every pairing. Figure 7.4 shows exactly how close it gets.

07.2Building a palette

Step 1: Establish the primary colour, and separate brand from action

Most palettes start from a brand colour. The first discovery is usually that the brand colour, at its exact brand value, can't be used for text or for buttons with white labels. Layer One's own signal orange, #ff6b3d, is a good example: it has a contrast of 2.83:1 on white, below the 4.5:1 WCAG 2.2 AA minimum for body text and below 3:1 for UI components. On the ink background it reaches 6.87:1. [[std]]

The answer is not to change the brand. It is to treat the brand colour as a seed for a ramp, and to choose ramp steps by role. The exact brand value is kept for large brand moments (illustration, the logo, dark-background accents), and a darker step from the same ramp is used for interactive elements on light backgrounds. In the palette below, the brand ramp is generated from #ff6b3d (oklch(0.705 0.191 37)), and brand.700 becomes the primary action colour.

Step 2: Choose supporting hues by job, not by taste

A product palette needs far fewer hues than a brand palette. Most products need:

HueJobRule
Brand / primaryPrimary actions, selection, key brand momentsOne hue; not reused for status
NeutralText, surfaces, borders, most of the interfaceLow chroma, often tinted toward the brand or a cool hue
Danger (red)Errors, destructive actionsNever the same hue as brand
Success (green)Confirmation, positive statusAlways paired with an icon or label
Warning (amber)Caution, pending statesDark text on amber, not white
Info / link (blue)Links, informational messages, focus ringsMay double as primary if brand is blue

Status colours must never carry meaning on their own. WCAG 2.2 success criterion 1.4.1 ("Use of Color") requires that colour is not the only visual means of conveying information,[[c:wcag22]] so every status colour ships with an icon, a label or both. [[std]]

Watch for collisions between brand and status hues. Ledgerly's brand orange sits at hue 37° and its danger red at 25°, only 12° apart. That's a realistic situation for a warm brand, and it means colour alone could never tell "primary action" from "destructive action". The fix is structural, not chromatic: destructive buttons get an explicit label and confirmation, and errors always carry an icon.

Step 3: Build ramps on a fixed lightness curve

A ramp (also called a scale or tonal palette) is the set of lightness steps for one hue. The key move in OKLCH is to fix the lightness of each step across all hues: blue.700, red.700 and neutral.700 all have L ≈ 0.485. That makes the step number itself meaningful.

The curve is denser at both ends than in the middle. Interfaces need many very light tints (surfaces, hover backgrounds, selected rows) and several very dark values (text, dark-mode surfaces), but only a few mid-tones. Radix Colors takes a similar purpose-led approach with 12 steps, each assigned a job from app background to high-contrast text;[[c:radix-scale]] Material 3 generates tonal palettes from a key colour in its HCT colour space.[[c:m3-color]] [[doc]]

Step 4: Shape chroma, then fit it to the gamut

Colourfulness should peak in the middle of the ramp and fall away toward both ends. Very light tints with high chroma look neon; very dark shades with high chroma look muddy. Our generator multiplies each hue's peak chroma by an envelope (the second row of the table above), then reduces chroma wherever the result falls outside sRGB. Lightness and hue are preserved, so contrast stays predictable.

Step 5: Validate contrast, and learn the pairing rules

WCAG 2.2 sets three thresholds you'll use constantly:[[c:wcag-contrast,wcag-nontext]] [[std]]

4.5:1Minimum for body text (AA, SC 1.4.3). 7:1 for AAA (SC 1.4.6).
3:1Large text: at least 18pt, or 14pt bold (about 24px / 18.66px).
3:1Non-text: UI component boundaries, focus indicators, meaningful graphics (SC 1.4.11).

Because lightness is fixed per step, contrast between two steps depends mostly on how many steps apart they are. That gives your team pairing rules they can apply without a contrast checker:

What about APCA?

APCA (the Accessible Perceptual Contrast Algorithm) is a newer contrast method that accounts for font size, weight and polarity, and it has been explored for future versions of WCAG.[[c:apca]] Radix Colors, for example, tunes its text steps to APCA targets.[[c:radix-scale]] It is promising, but WCAG 2.x contrast remains the normative requirement for conformance today. Validate with WCAG 2 ratios, and use APCA as additional guidance for dark mode and thin type if you wish.

07.3Neutrals: the colour you use most

In a typical product, neutrals cover far more of the screen than any other colour: text, backgrounds, surfaces, borders, dividers, disabled states. A carefully built neutral ramp does more for perceived quality than any brand colour.

Pure grey or tinted?

Pure greys (chroma 0) can feel cold and slightly "dead" next to a saturated brand colour. A very small amount of chroma (0.005–0.02 in OKLCH) tinted toward the brand hue (warm) or toward blue (cool) makes neutrals feel intentional. Ledgerly's neutral ramp uses chroma 0.018 at hue 260: a cool, barely visible tint. [[prac]]

How many neutral steps?

Use the same 11 steps as every other ramp so the pairing rules apply. In practice, light themes use about six neutral steps (50, 100, 200, 500, 700, 950) and dark themes about six more. Unused steps are cheap to keep and prevent ad-hoc greys later.

Common mistake

Light grey text

Low-contrast grey text for "secondary" information is the single most common accessibility failure on the web. WebAIM's 2025 scan found low-contrast text on 79.1% of the top million home pages.[[c:webaim-2025]] Fix it at the token: color.text.secondary in Ledgerly maps to neutral.700 (5.99:1 on the canvas), never to anything lighter.

07.4Colour architecture: primitive, semantic and component tokens

A palette is a set of values. A colour system is the layer of meaning on top of it. Mature public systems (Atlassian, Carbon, Spectrum, Salesforce Lightning, Material) all separate raw values from usage, even though their names differ.[[c:atlassian-tokens,carbon-themes,spectrum-tokens,slds-tokens]] [[doc]]

Why separate raw values from usage?

Themes become a remap, not a rewrite

Dark mode changes which primitive each semantic token points to. No component changes.

Meaning survives refactoring

If danger moves from red.700 to red.800, you change one reference, not every red in the product.

Decisions are reviewable

"Is text.secondary accessible?" is one check. "Are all the greys used for secondary text accessible?" is an audit.

The palette stays closed

Designers and engineers choose from roles, not from 66 swatches, so new ad-hoc colours stop appearing.

Do you need component tokens?

Component tokens add a level of indirection, and that has a cost: more tokens to name, document and maintain. Use them when (a) you support multiple brands or white-label theming that must restyle specific components, or (b) one component legitimately differs from the semantic default. Otherwise, components can consume semantic tokens directly. Many teams start with two tiers and add the third when theming demands it. [[prac]]

Brand tokens

In a multi-brand system, add a brand tier between primitives and semantics: each brand defines its own primitive ramps (or just its seed hues, from which ramps are generated), and the semantic tier references brand.* rather than a specific hue. Swapping the brand tier restyles every product. With OKLCH-generated ramps, a new brand needs only a seed colour; the lightness curve guarantees the same contrast behaviour.

Naming semantic colour tokens

Use a consistent grammar so people can guess names they haven't seen. Rule #3 of how we work is "name things so people can guess them". A grammar that works across most products:

color.{category}.{role}.{variant?}.{state?}

color.bg.surface                      // backgrounds: canvas, surface, subtle, inverse
color.text.secondary                   // text: primary, secondary, disabled, inverse, link
color.border.strong                    // border: default, strong, focus
color.icon.subtle
color.action.primary.bg.hover         // interactive: role → part → state
color.feedback.danger.text            // status: danger, warning, success, info

07.5Interactive and state colours

Interactive elements need a colour for each state: default, hover, pressed (active), focus, selected and disabled. There are two common strategies:

Strategy A — Step shift

Move along the ramp

Hover moves one step darker (light mode) or lighter (dark mode): brand.700 → brand.800. Explicit, easy to check for contrast, and every state is a named token.

DefaultHoverPressedFocus
Strategy B — State layers

Overlay a translucent layer

A semi-transparent layer of the content colour is placed over the component on hover or press. Material Design uses this approach. It works with any background, and fewer tokens are needed.

Default+ hover layer+ press layer

Focus deserves special care. A focus indicator is non-text content that must reach 3:1 against adjacent colours.[[c:wcag-nontext]] Use a dedicated color.focus.ring token (Ledgerly: blue.600 in light mode, 4.28:1 on the canvas). Don't reuse the brand colour, which may not contrast with the component it surrounds. Disabled elements are exempt from contrast requirements under WCAG, but they should still be legible enough to be recognised. Never rely on disabled styling alone to explain why something can't be used.

07.6Themes: light, dark, brand and white-label

With a semantic tier in place, a theme is simply a complete mapping from semantic tokens to primitives. The figure below shows the same mini-interface built from the same semantic tokens, rendered through two mappings.

Dark mode is not inversion

  • Don't use pure black. Very dark neutral surfaces (Ledgerly: neutral.950, L 0.255) reduce glare and leave room for elevation.
  • Express elevation with lighter surfaces. Shadows barely show on dark backgrounds. Raised surfaces step lighter (neutral.900, neutral.800).
  • Lighten, and often desaturate, accents. Ledgerly's primary action moves from brand.700 to brand.400 in dark mode, with dark text on top (5.96:1).
  • Re-validate everything. Pairings that pass in light mode can fail in dark mode, and vice versa.

Carbon, for example, ships four themes (two light, two dark) from a single set of semantic tokens.[[c:carbon-themes]] [[doc]]

[[prac]] White-label safely

Let customers pick a seed colour, then generate their ramp with your lightness curve and map your semantic tokens to it. Because lightness is fixed per step, a customer's "brand.700" lands at the same lightness as yours, so contrast survives a choice you didn't make. Validate the generated pairings automatically and fall back to a darker step where a hue misses (as green does at 600).

07.7Practical questions

How many colours should a design system contain?

Few hues, many steps, and fewer semantic tokens than you expect.

A typical product needs one brand hue, one neutral, and three or four status hues: five to seven ramps. At 11 steps each, that's 55–77 primitives, but only 30–60 semantic tokens, and those are what people actually choose from. [[prac]]

How many shades should a ramp have?

Between 10 and 13 steps is the established range.

Tailwind uses 11 (50–950), Radix 12, and Material's tonal palettes 13 tones.[[c:tailwind-v4,radix-scale,m3-color]] [[doc]] Fewer than about 9 leaves gaps for states and dark mode; more than about 13 produces steps nobody can tell apart.

Is there a maximum number of colours?

There's no standard maximum, but there is a practical one: what your team can tell apart and remember.

The symptom of too many colours isn't the palette size. It's semantic tokens with overlapping meaning (text.muted, text.subtle, text.secondary, text.tertiary). If two tokens can't be explained differently in one sentence, merge them.

How do we stop colour proliferation?
  • Components consume semantic tokens only; lint against raw colour values in product code.
  • New semantic tokens need a reason ("which role doesn't exist yet?") and an owner's approval.
  • Run the "unique colours in code" count from Chapter 03 every quarter. It should fall.
How should we handle gradients?

Interpolate in OKLCH and tokenise the stops.

Blending in sRGB passes through a dull, greyish midpoint; OKLCH keeps the midpoint vivid and evenly bright. CSS lets you choose the interpolation space directly.

linear-gradient(in srgb, blue.600, amber.400)
linear-gradient(in oklch, blue.600, amber.400)
What about overlays and transparency?

Use transparency for overlays and state layers, never for text.

Scrims behind dialogs (color.overlay.scrim → oklch(0.2 0.02 260 / 0.5)) and state layers are good uses of alpha. Text with alpha is not: its contrast changes with whatever is behind it, so it can't be validated once. Give text solid tokens.

Colour system checklist

  • Palette built in OKLCH from a fixed lightness curve
  • Brand colour used as a seed; action colour is a text-safe step
  • 5–7 ramps, 10–13 steps each, same step numbers across hues
  • Gamut mapping applied; hex fallbacks generated, not hand-picked
  • Neutral ramp with a deliberate tint (or a deliberate lack of one)
  • Pairing rules published for designers
  • Primitive and semantic tiers; components never reference primitives
  • Token naming grammar documented
  • State colours defined for every interactive role, including focus
  • Light and dark themes as semantic mappings
  • Every semantic pairing contrast-tested automatically in CI
  • Status colours always paired with icon or text
