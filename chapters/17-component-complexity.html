Chapter 17

Component complexity

A badge and a data table are both "components", but one takes an afternoon and the other can take a quarter. Understanding complexity helps you plan honestly, choose the right process for each component, and pick the simplest component that does the job.

Read this if

You estimate or plan component work, keep being surprised by how long some components take, or need to decide which component to use for a design problem.

What you'll leave with
  1. Four clear levels of component complexity, with examples.
  2. A scoring method you can use to rate any component.
  3. How complexity should change your process, and how to keep it under control.

17.1Not all components are equal

Here's a planning conversation we hear all the time. "This quarter, the design system team will build ten components: tooltip, badge, avatar, divider, tag, button group, breadcrumbs, tabs, date picker and data table." Ten components, three months, so about a week each. It sounds reasonable. It isn't.

Scenario"Ten components this quarter"
The situation

A system team commits to ten components in a quarter. The first six (badge, avatar, divider, tag, tooltip, breadcrumbs) are done in three weeks. The team feels ahead of schedule.

What goes wrong

Tabs take two weeks to get keyboard behaviour right. The date picker takes five weeks: time zones, locales, keyboard grids, screen readers. The data table isn't started. Leadership sees "60% done" and loses trust.

What would have helped

Rating each component's complexity first. The data table alone was more work than the other nine combined. The plan should have said so, or left it for next quarter.

Counting components is like estimating a house renovation by counting rooms: the bathroom and the hallway are both "a room", but one involves plumbing, waterproofing and tiling. Complexity is what tells you which is which. The rest of this chapter gives you a shared language for it, so designers, engineers and managers can plan together and stop being surprised.

17.2Four levels of complexity

We find it useful to sort components into four levels. They loosely echo Brad Frost's idea of building from small parts to large ones,[[c:frost-atomic]] but they're organised by how hard something is to get right rather than how big it is.

Level 1, elements, mostly display something: a badge, an avatar, a divider, an icon. They're about visual consistency and they're quick to build. The main risk is making too many variations of them.

Level 2, controls, are the things people interact with directly: buttons, text fields, checkboxes. Each has one main job, but now every state matters (hover, focus, disabled, error), and keyboard and screen-reader support become essential.

Level 3, composites, are built from several parts that have to work together: a menu has a trigger and a list; tabs have a tab list and panels; a dialog manages focus for everything inside it. This is where accessibility gets genuinely hard, because there are established keyboard patterns people expect, documented in the W3C's ARIA Authoring Practices Guide.[[c:aria-apg]]

Level 4, systems, are small applications in their own right. A data table sorts, filters, paginates, selects rows, resizes columns and must stay fast with thousands of rows. A rich text editor is a famously hard engineering problem. These components often take longer than everything else in the library combined.

17.3Measuring complexity: a simple scoring method

Levels are a good first guess, but you'll want something more precise when planning. Here's a scoring method we use. Rate the component from 0 to 3 on each of eight questions, then add them up. You don't need to be exact; the point is to have the conversation, as a team, before committing to dates. [[prac]]

17.4How complexity changes the way you work

Here's the practical payoff. Once you know a component's level, you can match the process to it. Running a level 4 process for a badge wastes everyone's time; running a level 1 process for a data table guarantees bugs in production.

Level 1 · ElementsLevel 2 · ControlsLevel 3 · CompositesLevel 4 · Systems
Who's involvedOne designer, one engineerPair, plus a quick accessibility checkPair, accessibility specialist, a pilot teamA small squad, several pilot teams, product managers
ResearchInventory onlyInventory and real contentUsage research across teamsRequirements gathering, like a product feature
AccessibilityContrast, labelsKeyboard and screen-reader basicsFull ARIA pattern; manual testingExpert review; testing with assistive-technology users
TestingVisual testsVisual and behaviour testsPlus manual keyboard and screen-reader testsPlus performance tests with real data volumes
Beta periodNone neededA week or twoA month, with a pilotA quarter, with several pilots
DocumentationShort pageFull templateFull template plus behaviour notesGuides, recipes and examples
Typical effortDays1–2 weeks3–6 weeks1–3 months or more

Effort ranges are [[prac]] estimates for one web framework, assuming foundations already exist. Each extra platform adds roughly the same again.

[[prac]] Plan by points, not by count

Instead of "ten components this quarter", plan with the complexity totals: "about 90 points this quarter". A badge is 2 points, a data table is 22. It sounds a little nerdy, but it instantly makes plans more honest, and it gives leadership a much better picture of progress than a count of finished components.

17.5Choosing the simplest component that works

Complexity isn't just a planning tool for system teams. It's also a design decision for product teams. Every time a designer chooses a component, they're choosing a level of complexity for their users and for the engineers who'll build the screen. The simplest component that does the job is almost always the right choice.

If you need people to…Prefer this (simpler)Over this (more complex)Unless…
Choose one of 2–5 optionsRadio buttonsA dropdown selectSpace is very tight
Choose one of 6–15 optionsA selectA searchable comboboxOptions are unfamiliar or long
Choose from hundreds of optionsA combobox with searchA custom picker dialogOptions need images or grouping
Enter a date they know (birthday)Three simple fields or one text fieldA calendar date pickerThey need to see days of the week
Show extra informationText on the pageA tooltipIt's genuinely secondary
Confirm a decisionAn inline message or undoA confirmation dialogThe action is destructive and can't be undone

The date example is worth a moment. Calendar pickers feel modern, but for a date someone already knows, like their date of birth, typing it is usually faster than scrolling back decades in a calendar. The GOV.UK Design System, which is heavily user-tested, recommends simple separate day, month and year fields for exactly this case.[[c:govuk-patterns]] [[doc]] Simpler for the user, and a level 2 component instead of a level 3.

When you do need something complex, build it from simpler parts. A combobox is a text field plus a list plus some coordination; a data table is cells, checkboxes, buttons and menus arranged in a grid. If the simple parts are solid, the complex component inherits their quality, and fixes to the parts improve everything built from them.

17.6Keeping complexity under control

Components tend to get more complex over time. Every reasonable request adds a little: one more option, one more state, one more special case. We call this complexity creep, and it's how a level 2 button quietly becomes a level 3 problem nobody wants to touch.

Three habits keep it in check. The first is a scope statement on every component's documentation page: a short list of what this component will never do. "The button will never contain a dropdown. Use the split button instead." It sounds negative, but it saves enormous amounts of debate.

The second is splitting instead of stretching. When a component starts serving two quite different jobs, it's usually better to split it into two simpler components than to add options until it does both badly. A "card" that is sometimes a link, sometimes a form and sometimes a dashboard widget is probably three components.

The third is re-scoring once a year. Run the eight questions again for your most-used components. If a score has jumped, ask why, and whether all that complexity is still earning its keep.

A mistake we see often

Building the "universal" component

A team tries to build one table that handles every possible case: simple lists, editable spreadsheets, trees, pivot tables. It takes a year and is so complex that most teams avoid it. It's usually better to build a simple table that handles 80% of cases well, and let the rare, complex cases use a specialised component or a well-chosen third-party library.

The short version

What to remember from this chapter

  1. Components range from simple elements to whole systems. A data table can be more work than ten badges.
  2. Score components on eight questions to plan honestly, and plan by points, not by count.
  3. Match the process (people, testing, beta period) to the level of complexity.
  4. Choose the simplest component that works, and fight complexity creep with scope statements and splits.
